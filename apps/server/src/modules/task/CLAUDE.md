# task 모듈

## 하는 일
에이전트가 일하고 주인이 결재하는 구조. 러너가 일을 빌려 가고, 위험한 동작은 결재를 거치고, 결과가 오면 작업을 끝낸다.
설계는 docs/객체설계.md 13장, API는 docs/API설계.md, 표는 docs/테이블설계.md 6장.

- `agent/`: 에이전트 (`Agent`). 결재로 맡길 동작, 토큰 한도(한 달 · 5시간), 구독 사용률 멈춤값. `api/agents`. 팀 없는 같은 일꾼 (2026-11-21, 기획서 결정): 보고 라인 · 팀장 · 팀 템플릿이 없고 권한은 모두 같다 (`AgentScopes.check`가 늘 전부를 돌려준다, 모르는 이름만 막는다). 새 에이전트는 사이트 클릭 · 로그인 승인 동작(`Agent.BROWSE_ACTIONS`)으로 시작한다.
  역할 일꾼 (2026-11-28, 기획서 결정): 공간마다 일곱 역할 일꾼(planner 기획자 · researcher 리서처 · writer 작가 · maker 디자이너 · developer 개발자 · reviewer 검토자 · browser 브라우저 담당)을 서버가 늘 갖춘다. 정의는 `agent-roles.json`(`AgentRoles`: 이름 · 맡길 종류 `kinds` · 역할을 고르지 않았을 때 받을 종류 `defaults` · ECC형 역할 설명), 일꾼 쪽 열쇠는 `agents.preset`(공간마다 살아 있는 것 하나, 대표에는 없음). `AgentRoster.ensure`가 대표를 처음 만들 때(`AgentEdit.lead`)와 서버를 켤 때(`AgentService.onApplicationBootstrap`, 대표가 있는 공간마다 `lockLeadSlot` 뒤) 없는 역할을 대표의 AI 도구로 만들고(`Agent.openPreset`) 이름 · 역할이 정의와 다르면 맞춘다(설정 판). 대표에게 검토자가 없고 검토자 역할 일꾼의 도구가 대표와 다르면 짝짓는다. 관리자는 역할 일꾼의 이름 · 역할을 바꾸지 못하고(`AgentRoles.assertEdit`, 같은 값은 됨) 지우지 못한다(`Agent.delete`). 예전 일꾼 N(2026-11-23 `task_plain_workers`)은 막힌 것이 없으면 마이그레이션 `task_role_workers`가 휴지통으로 옮겼고, 남은 것은 그대로 일한다. 만들기 API(`POST api/agents`)는 서버에 남아 있고 화면에서만 뺐다
  대표 (O-2, 서브나 14장, `agents.lead`, 규칙은 `AgentLead`): 공간마다 숨은 에이전트 하나가 모든 대화 · 대화로 보내는 스케줄 · `ask_agent`를 받는다. 없으면 `AgentEdit.lead`가 만든다(advisory 잠금, 도구는 서버의 로그인 순서). 목록 · `get_settings team`에 보이지 않고 `GET api/agents/lead`로만 읽는다. 관리자는 이름 · 도구 · 모델 · 강도 · 한도 · 검토자만 바꾸고(`AgentLead.assertEdit`) 지울 수 없다. 이름 (2026-11-24): 처음은 `AgentLead.DEFAULT_NAME`(아리, 마이그레이션 `task_lead_name`이 옛 "대표"도 바꾸고 설정 판을 쌓았다), 지시문의 intro가 그 이름으로 소개하고 화면은 "이름 (대표)"로 보인다. 맡기기는 대표만, 한 층이다: 대표는 지우지 않은 일꾼 누구에게나 맡기고(`Agent.manages` → `AgentLead.leads`), 일꾼은 맡기지 않고 `ask_help`로 대표에게 나눌 부분을 알린다. 담당 없는 일을 자동 배정할 때는 대표를 고르지 않는다 (`JobService.lease` · `lockNext`)
  삭제는 휴지통 (`deleted_at`, 2026-11-14): `Agent.delete` · `restore`. 진행 중인 작업 · 스케줄 · 도는 목표 실행이 있으면 지우지 않는다 (`AgentQuery.blockers`). 지운 에이전트는 `AgentRepository.load` · `lock`에서 NotFound, `usage`(일 빌리기) · `manages`(위임)에서 빠진다. 줄은 지우지 않는다 (실행 기록이 가리킨다)

- `external-tool/`: 외부 도구 꽂기 (2차 7단계, `ExternalTool`, 주소 규칙 `ExternalToolUrl`). 원격(https) MCP 하나. `api/external-tools`(관리자만: 목록 · 더하기 · 고치기 · 켜기/끄기 · 토큰 넣기 · 지우기), MCP `propose_tool`(작업 토큰, 모든 에이전트). 제안은 `proposed`로 두고 AI가 `request_approval`(`task.tool.plug`, 대상 `external_tool`)을 올린다. `ExternalToolPlugHandler`(`task.approval.*`)가 승인이면 켜고 제안한 에이전트에 붙여 결과(`task.external_tool.plugged` · `plug_failed`, approvalId · outcome)를 남기고, 승인이 아니면 제안을 지운다.
  토큰(머리글의 값)은 `SecretBox.seal`로 잠그고 어느 View에도 싣지 않는다 (`hasSecret`만). 푸는 곳은 일을 빌려 줄 때 `ExternalToolQuery.forJob` 하나: 그 에이전트가 허락한 이름 중 켜져 있고 토큰이 갖춰진 것만 `next_jobs`의 `tools`로. 서버 키를 바꾸면 `SecretRotation`(`task.external_tools`)이 다시 잠근다.
  연결 확인 · 도구 목록 · 사용 기록 (2026-11-15 MCP 1단계, [MCP](../../../../../docs/MCP.md)): 서버는 원격 MCP의 도구에 붙지 않는다(SSRF. OAuth 로그인 서버만 아래 C1의 `OAuthGateway`로). `POST api/external-tools/:id/check`와 `ExternalToolCheckJob`(마감 작업: 가장 이른 다시 확인 시각, 커넥터를 저장하면 `ExternalToolRepository.dueWake`가, 작업이 바뀌면 `task.task.changed`로 다시 잰다, 확인 전 · 고친 뒤 · 하루 지난 켜진 도구 20개까지)이 에이전트 없는 일 `tool_check`(`Task.AGENTLESS`, 우선순위 `AiTasks.PRIORITY`, 도구마다 기다리는 것 하나, `next_jobs`에 `connector_check`를 알린 러너에게만)를 만들고, 러너가 tools/list를 받아 `result.tools`로 끝낸다. `ExternalToolTaskHandler`(`task.task.changed`) → `ExternalToolCheckService.noteTask`가 끝난 작업을 읽어 확인이면 `catalog` · `checked_at` · `check_error`를(실패면 옛 목록을 둔다, 목록 칸 없이 끝나면 옛 러너라 실패), 에이전트의 일이면 결과의 `connector_calls` 중 그 에이전트가 허락받은 이름만 `last_used_at` · `last_failed_at` · `last_error`에 적고 `task.external_tool.noted`를 낸다. 이 칸들은 주인의 편집과 겨루지 않게 버전 없이 적는다(`noteCheck` · `noteUsage`, 시각은 앞으로만). 받는 값은 `ToolCatalog`로 거른다. 일을 빌려 줄 때 도구마다 `catalog` 줄(30줄 · 120자)을 실어 러너가 지시문 틀 `tools`에 쓴다(MCP 도구 → `read_url` → 브라우저 순서)
  도구 바뀜 감지 (C3, 2026-11-25, [MCP](../../../../../docs/MCP.md) 8장): 확인 결과가 승인한 `catalog`와 다르면(새 도구 · 설명 바뀜, `ToolCatalog.acceptable`) `ExternalToolRepository.holdCatalog`가 새 목록을 `catalog_pending` · 처음 바뀐 때를 `catalog_changed_at`에 두고 새로 멈췄으면 바로 알림(`TaskNotices.CONNECTOR_CHANGED`). 멈춘 커넥터는 `ExternalTool.usable`이 아니라 `forJob` · 일꾼 정보(`AgentRepository.roster`)에서 빠진다 (연결 확인은 `ready`라 계속). `POST api/external-tools/:id/catalog/approve { changedAt }`(관리자만, `ExternalToolCheckService.approveCatalog`)가 본 바뀐 때와 같을 때만 옮기고(아니면 409) 알림을 읽음으로. 주소를 바꾸면(`edit`) 승인한 목록을 비운다
  OAuth 커넥터 (C1, 2026-11-21, [MCP](../../../../../docs/MCP.md) 8장): 로그인 방식 `external_tools.auth`(header · oauth, oauth면 머리글 · 토큰 칸 없음, 주소 · 방식을 바꾸면 `ExternalTool.signOut`). 로그인의 흐름은 같은 줄의 엔티티 `ConnectorLogin`이 버전 없이 적는다(`ExternalToolRepository.login(…, lock)` · `saveLogin`: 연결하면 확인을, `token_refresh_at`이 바뀌면 갱신을 깨운다). `POST api/external-tools/:id/oauth/start`(`ExternalToolOAuthService.start`: 보호된 자원 정보 RFC 9728 → 로그인 서버 정보 RFC 8414 · OIDC → 처음이면 동적 등록 RFC 7591, 받은 값은 `OAuthMetadata`가 거른다(https · issuer 일치 · S256). state(커넥터 id . 무작위)와 PKCE 검증값은 `SecretBox.pack`(용도 `external-tool-oauth:<커넥터>`, 10분)으로 `oauth_pending`에) → 로그인 서버 → `GET api/external-tools/oauth/callback`(`finish`: `ConnectorLogin.take`가 state를 맞춰 한 번 꺼내고, 코드를 토큰으로 바꿔(`OAuthGrant.tokens`) 묶음을 `SecretBox.seal`로 `token`에, 실패 까닭은 `oauth_error`. 302로 커넥터 화면 `?connected` · `?oauth_error=state·denied·token·changed`(`OAuthStop`), 관리자가 아니면 403). 갱신은 마감 작업 `ExternalToolRefreshJob`(끝나기 10분 전 · 수명의 절반, 잠깐 실패(5xx · 바깥)면 5분 뒤, 거절 · 갱신 토큰 없음 · 곧 끝남이면 토큰을 지워 "로그인 필요"와 `task.external_tool.noted`). 늦게 온 갱신은 시작할 때의 토큰(nonce)이 그대로일 때만 적는다. 일을 빌려 줄 때 `ExternalTool.ready(now)`(접근 토큰이 1분 넘게 남음) · `jobView`가 `Authorization: Bearer`로 실어 러너는 그대로다. 서버가 바깥에 붙는 길은 `OAuthGateway` 하나: https만, 이름을 풀어 `web/public-address.policy.ts`(`PublicAddress`, read_url과 함께 쓰는 막을 주소)로 내부망 · 메타데이터를 막고 확인한 주소로만, GET 리다이렉트 3번까지 매번 다시, 10초 · 256KB, 본문 · 토큰은 로그 · 오류 글에 없다. 시험만 `MOIDA_OAUTH_TEST_LOOPBACK=1`(루프백을 그대로 적은 주소를 http로). 돌아올 주소는 platform `HostGate.siteOrigin`(사이트 주소, `modules.json` registries.asks `site`) 아래
  같은 모듈의 여러 묶음 (객체설계 4장 · 9장): 도구를 붙이고(승인) 떼는(지우기) 일은 에이전트의 허락 목록과 한 트랜잭션이라 `ExternalToolService`가 `AgentRepository`를 함께 쓴다 (잠그는 순서는 "지켜야 할 것"의 한 줄). 토큰을 푸는 읽기는 엔티티를 거친다 (`ExternalTool.jobView`, 객체설계 4장의 예외)

  부르기(`ApiCall`, `task.api_calls`): 열 때(`ApiCallService.open`, 잠그는 순서 작업 → 커넥터 → 부르기 → 결재) 쓰기(write) · 하루 한도(`daily_max`, 최근 24시간 spend 수 `ApiCallRepository.spentSince`)를 넘은 spend는 held로 두고 결재 `task.api.call`(`ApiApproval.call`)을 올린다(관리자의 시험은 누른 것이 승인이라 기다리지 않는다). 아니면 트랜잭션 밖에서 첫 요청 → `answered`(상태 묻기가 있으면 polling, 끝난 답의 파일 칸이 있으면 fetching). 마감 작업 `ApiCallJob`(`next_at`이 바뀌면 저장이 깨운다)이 `ApiCallService.due`로 맡고(`claim` 10분) 상태를 묻고(`polled` · `pollMissed`), 파일은 키 없이 받아(`ApiCallGateway.download`) `OutputService.keepFetched`로 부른 일의 실행에 결과물로 남긴다(`filesKept`, 주소는 지운다). 결재가 정해지면 `ApiDecisionHandler`(`task.approval.*`) → 커넥터는 `ApiConnectorService.decide`(승인 `plugApproved`: 켜기 · 새 버전으로(앞 정의서 `history` 10개), 결과 `task.api_connector.plugged` · `plug_failed`로 작업이 끝남. 아니면 새 제안은 지우고 새 버전 제안만 버림), 부르기는 `ApiCallService.decide`(승인이면 한 번 부르고 `task.api_call.ran` continue로 기다리던 작업을 다시 대기열에, 아니면 refused). 두 결재는 `request_approval`로 올리지 못한다(`ApiApproval.SERVER_ONLY`). 잇기는 `task-connectors.ts`(`TaskConnectors`: 핸들러 · 마감 작업 · 키 다시 잠그기 `task.api_connectors`)

- `goal-run/`: 목표 실행 (`GoalRun`, 회차 보고 `GoalRound`, 기획서 결정 2026-11-13). 주인이 목표 하나를 에이전트에게 맡기면 회차(작업 하나)가 저절로 이어 돌고, 주인은 중간 · 최종 결재문만 받는다. `api/goal-runs`(주인만: 목록 · 상세 · 시작 · 멈추기), MCP `report_round`(작업 토큰, 회차마다 한 번). 회차 작업이 끝나거나(`task.task.changed`) 결재가 정해지면(`task.approval.*`, 대상 `goal_run`) `GoalRunHandler`가 다음을 정한다
- `web/`: 주소 읽기 (MCP `read_url`, 작업 토큰). 서버가 AI 대신 페이지를 열어 글자만 준다 (`WebQuery`). 목줄은 `WebReach`: 공개 주소 어디든 (2026-11-21, 모두 비공개를 읽는 같은 일꾼이라 "지시에 적힌 사이트만"은 없앴다). http · https만, 아이디 · 비밀번호가 든 주소는 막는다. 내부망 · 이 서버 · 메타데이터 주소는 이름을 풀어 본 뒤 그 주소로만 붙어 막는다 (`WebPageGateway`, 리다이렉트 3번까지 매번 다시). 2MB · 15초, 글이 아닌 형식은 거절. 받은 글은 자료라는 표시(`note`, 지시문 틀 `read-url-note`)와 함께.
  링크 미리보기 (F3, 2026-11-21, `LinkPreviewQuery` · `api/link-preview`, 관리자만): 대화의 답에 있는 주소를 같은 길로 열어 제목 · 사이트 · 설명 · 대표 그림(메타 태그, `HtmlText.meta`)만 카드로. 읽은 주소는 하루 · 열지 못한 주소는 10분 프로세스 메모리에 500개까지. 그림은 미리보기한 페이지의 대표 그림만 서버가 받아 준다(`WebPageGateway.image`: 앞부분으로 알아본 PNG · JPEG · GIF · WebP, 1MB): 아무 주소의 그림을 대신 받아 주는 길이 되지 않게, 관리자의 브라우저가 바깥 사이트에 직접 닿지 않게
- `skill/`: 러너 스킬의 콘솔 판 (`Skill`, 파일 규칙과 해시 `SkillFiles`, 쓸 판 고르기 `SkillPackage`, 저장소 판 읽기 `RepoSkillGateway`). `api/runner-skills`. `next_jobs`의 `skill_package`로 러너에게 간다. 스킬 하나의 응답에는 버전마다의 성적표가 있다 (`SkillScore`, 2026-11-24: `task_runs`의 처음 실행으로 버전을 정하고 끝냄 · 수정 요청 · 반려 · 실행 수 · 토큰을 센다. 끝난 일이 적으면 판단 보류).
  지시문 틀 (`moida-runner`, 2차 1-0 · 기획서 결정 2026-11-14): AI에게 가는 지시문의 글. 에이전트의 일마다 `prompt_package`로 지금 판을 보내고(러너가 채운다), 서버가 만드는 글(목표 실행의 회차 지시 `goal-round` · 앞 회차 보고 `goal-report`, `read_url`의 알림 `read-url-note`)은 `SkillQuery.prompts` → `PromptTemplates.fill`로 채운다 (콘솔 판에 없는 틀은 저장소 판에서). 콘솔 판은 저장소 판과 틀 이름 · 자리 · 여닫는 표시가 맞아야 쌓인다 (`PromptTemplates.assertFits`, `Skill.addRevision`). 실행 기록에 판(`prompt_source` · `prompt_revision` · `prompt_hash`)을 남긴다

파일 구조 (객체설계 6장): `<이름>.ts` · `.view.ts` · `.input.ts` · `.service.ts` · `.query.ts` · `.api.ts` · `.tool.ts` · `.repository.ts`.
엔티티는 `TableEntity`(platform)로 표 한 줄을 들고 바뀐 칸을 기억하고, Repository(`TableRepository`)는 그 칸만 저장한다. 칼럼을 아는 곳은 `task.tables.ts`, Entity의 `RULES`, Input의 `COLUMNS`, View의 `toJSON`이다.
도구 모양은 docs/API설계.md 4장이 원본이다. `report_progress`는 기록을 모아 받고, 러너가 쓰므로 바꾸면 `apps/runner`도 함께 고친다.

## 데이터 묶음
- 에이전트: agents + agent_revisions (설정 판은 `settings_revision`. 보고 라인 `reports_to`는 2026-11-21에 지웠다)
- 외부 도구: external_tools (허락은 에이전트의 `external_tools`라 에이전트 묶음에 저장한다)
- API 커넥터: api_connectors / API 부르기: api_calls (커넥터를 지우면 함께, 결과물은 결과물 묶음에)
- 대화: chats + chat_updates (회차 · 덧붙인 말의 답은 tasks의 줄이라 작업 묶음에 저장한다)
- 목표: goals
- 스케줄: schedules (에이전트 하나에 여럿, 담당 없이 자동 배정도)
- 작업: tasks + task_events + task_runs (빌려 줄 때마다 규칙 판 한 줄)
- 스킬: skills + skill_revisions
- 결과물: outputs (파일은 platform.blobs를 값으로)
- 결과물 공유: output_shares (결과물을 바로 지우면 함께 지워진다, 외래키 CASCADE)
- 목표 실행: goal_runs + goal_rounds (회차 작업은 tasks의 줄, 결재는 approvals의 줄이라 각자의 묶음에 저장한다)
- 결재: approvals
- 판정: verdicts (판정 작업 · 판정받은 에이전트는 tasks · agents의 줄을 가리킨다)
- 배운 규칙: learned_rules + rule_marks (세기의 근거는 규칙과 함께 저장한다. 판정을 남기는 `VerdictService`가 같은 트랜잭션에서 센다)
- 구독 사용률: plan_usage (창마다 마지막 값 하나. `window`는 Postgres 예약어라 열은 `period`, API는 `window`)
- AI 로그인: ai_logins (공간과 도구마다 한 줄)
- 러너: runners (러너 기기마다 한 줄, 처음 닿을 때 생긴다)

## 공개 API (`index.ts`)
`TaskModule`, `TaskTools`(mcp 모듈이 모아서 연다. 도구 클래스 목록 `TaskTools.PROVIDERS`를 `TaskModule`이 providers에 펼친다), `TaskQuery`(`isLive`: mcp 입구가 호출마다 작업 토큰이 살아 있는지 묻는다). 기능 패키지에게는 platform의 `Leases`에 `TaskQuery.leasedWork`를 등록해 "이 러너가 지금 쥔 작업"(id · 종류 · 보인 입력 · 대상 · 지시 · 관리자가 쓴 지시 `TaskQuery.ownerText`)을 알려 준다 (`work.leased`, code-github · browser-tabs의 사이트 · 클릭). vault에게는 platform `Leases.registerRecord`에 `TaskQuery.recordTarget`을 등록해 실행 기록의 자리(그 러너의 마지막 실행 · 세션 키 · 작업 세션 키와 제목 · 에이전트)를 알려 준다 (2026-11-17, 작업 세션). `Leases.registerSettled`에는 `TaskQuery.settledFlow`를 등록해 작업 세션의 요청이 끝났는지(맨 위 작업 완료 · 대화는 가라앉고 카드를 기다리지 않음 · 결과 카드 승인 → 끝, 실패 · 취소 · 카드 반려 → 원문으로만, 판단은 `RunLineage.settledOf` · `settledCard`)를 알려 준다 (S2, 2026-11-28). 기능 패키지의 대화 입구는 platform `PluginChats`에 `ChatTalk.fromPlugin`을 등록한다 (플러그인 API 0.10, 2026-11-23 텔레그램)

## 내보내는 이벤트
칸의 원본은 `task.events.json` (리팩토링 R3c): 여기는 뜻을 적고, 칸이 바뀌면 그 파일을 고친다. 목록에 없는 주제 · 칸은 내보낼 때 막힌다.

| 이벤트 | 내용 |
|---|---|
| `task.task.changed` | `taskId, status, title`, 실패면 `error`(앞 300자). 상태가 바뀔 때마다 |
| `task.external_tool.noted` | `toolId` 또는 `names`. 커넥터의 연결 확인 결과 · 사용 기록을 적음 (2026-11-15 MCP 1단계, 화면이 다시 읽는다) |
| `task.external_tool.plugged` · `plug_failed` | `toolId, name?, agentId?, approvalId, outcome`, 실패면 `error`. 제안한 외부 도구의 결재(`task.tool.plug`)를 실행한 결과 (2차 7단계, 받는 쪽은 `ApprovalResultHandler`) |
| `task.agent.changed` | `agentId, status` |

| `task.chat.said` | `chatId, title, kind, taskId, text`(앞 3500자), `mail?`. 관리자에게 돌아가는 말: 회차의 최종 답(`final`) · 덧붙인 말의 답(`reply`) · 회차 실패(`failed`) (2026-11-23, 받는 쪽은 메신저 기능 패키지 `messenger-telegram`). `mail: true`는 메일로 받는 자동화의 회차(2026-11-27, 받는 쪽은 `email`) |
| `task.chat.changed` | `chatId, turns`. 대화를 열거나 메시지를 보낼 때마다 (화면이 다시 읽는다. 받는 모듈은 없다) |
| `task.rule.changed` | `ruleId, status`. 배운 규칙을 만들거나 내리거나 되살릴 때 (화면이 다시 읽는다. 받는 모듈은 없다, 2026-11-28) |
| `task.goal_run.changed` | `goalRunId, goalId, status, round`. 실행의 상태 · 회차가 바뀔 때마다 (화면이 다시 읽는다. 받는 모듈은 없다) |
| `task.approval.requested` · `granted` · `rejected` · `revision_requested` · `cancelled` · `inspected`(검수가 끝남, 2026-11-20) | `approvalId, taskId, agentId, action, targetKind, targetId, targetVersion, decidedBy, note, chatId`(대화의 결재면 그 대화, 2차 2단계), `payload`(설정 바꾸기의 바뀔 값, 다른 결재는 null, 2026-11-15 C) |

| `task.api_call.ran` | `callId, approvalId, outcome: continue`. 승인한 API 부르기를 한 번 보냈다: 기다리던 작업이 이어서 한다 (2026-11-24) |
| `task.setting.changed` | `approvalId, outcome`, 실패면 `error`. 승인한 에이전트 · 스케줄 · 목표 설정 바꾸기를 적용한 결과 (받는 쪽은 `ApprovalResultHandler`. 다른 모듈의 설정은 `<모듈>.setting.changed`) |

`task.approval.granted`를 받은 모듈이 동작을 실행한다. 받는 모듈이 `CoreWorkers.expect`도 적는다 (지금은 blog의 `blog.post.publish`). 실행하는 모듈이 없는 동작은 승인해도 작업이 끝나지 않는다. 기능 패키지의 동작도 같다: `browser.site.publish`(대상 `browser_click`)는 `browser-tabs`가 받아 붙잡은 러너가 같은 버튼인지 보고 누른 뒤 결과를 남긴다. `browser.site.login`(대상 `browser_site`)은 "로그인했어요"(수정 요청)로 작업을 다시 대기열로 돌리는 결재라 승인은 실패로 끝난다 (패키지가 꺼져 있으면 끝나지 않으니 작업을 취소한다). 두 결재는 AI가 아니라 러너가 작업 토큰으로 올린다.
변경 신호(SSE)만 있고 이벤트가 아닌 것: `task.event.added` (실행 기록이 쌓임, id는 작업), `task.usage.changed` (구독 사용률이 옴, id는 도구).

## 알리는 것 (`TaskNotices`, 7단계)
`onModuleInit`에서 platform의 `NoticeCatalog`에 등록한다. 알림 글과 주소는 여기서 정하고, 어디로 · 언제 보낼지는 platform이 정한다.
- `task.approval.requested` 결재 요청 (즉시): 결재가 올라오면. 결재가 끝나면(승인 · 거절 · 고쳐 달라 · 취소) 그 알림은 읽음 (`approval:<결재>`). 대화의 결재(`chatId`)는 알리지 않고 결과 카드가 생길 때 한 번 ("결과를 골라 주세요", 대화로 가는 주소)
- `task.task.failed` 작업 실패 (즉시): `task.task.changed`의 `failed`에서. 본문은 이벤트의 `error`
- `task.chat.answered` 대화의 답 (즉시): 회차의 답. 메일은 기본 끔(`noMailByDefault`, 2026-11-27): 관리자가 알림 설정에서 켜거나, 자동화는 레시피의 "메일로 받기"로
- `task.schedule.stopped` 자동화 멈춤 (즉시): 레시피의 일이 3번 잇달아 실패해 끈 때 `ScheduleService.checkHealth`가 같은 트랜잭션에서 `Notices.post`로
- `task.schedule.skipped` 스케줄 한도 (기록만): 이벤트 없이 `ScheduleService`가 같은 트랜잭션에서 `Notices.post`로 (스케줄마다 한 줄)

## 받는 이벤트
- `task.task.changed`(자기 이벤트): 끝난 하위 작업이면 형제가 모두 끝났는지 보고 위 작업을 깨운다 (`SubtaskSettledHandler`). 끝난(완료 · 실패 · 취소) 회차 작업이면 목표 실행의 다음을 정한다 (`GoalRunHandler`)
- `task.approval.*`(자기 이벤트): 대상이 `goal_run`인 결재가 정해지면 목표 실행을 잇거나 닫는다 (`GoalRunHandler`). 결과 카드가 수정 요청 · 반려되면 대화의 도는 일을 멈추고 수정 요청이면 다음 회차 (`ChatCardHandler`)
- `task.task.changed` · `task.approval.requested` · `task.approval.inspected`(자기 이벤트): 대화의 일이 가라앉았으면 다시 맡김 · 검수 · 검토 · 결과 카드 (`ChatResultHandler`, 2차 2단계)
- `task.task.changed`(자기 이벤트): 끝난 검수 작업의 결정을 결재에 적는다 (`ChatInspectHandler`, 2026-11-20)
- `task.task.changed`(자기 이벤트): 끝난 검토 · 검수 작업의 판정을 `task.verdicts`에 (`VerdictHandler`), 실패한 레시피의 일이면 건강 검사 (`ScheduleFollowHandler`) (2026-11-20 평가가 남는 팀)
- `task.approval.revision_requested`(자기 이벤트): 관리자의 수정 요청 메모가 쌓였으면 대표에게 피드백에서 배우기 일 (`LessonHandler`, 2026-11-20), 그 일이 따른 배운 규칙의 해로움 (`RuleHarmHandler`, 2026-11-28)
- `blog.app_code.added`: 대화의 make 일이 만든 확인 대기 버전이면 그 대화의 결과 카드에 공개 승인 (`AppCodeCardHandler`, 스토어 1-6b). 그 밖은 넘어간다
- `task.agentless.requested`: 에이전트 없이 서버의 로그인으로 돌 일 (2차 4단계, 지금은 vault의 세션 노트). 내용 `requestId, kind, title, targetKind, targetId, baseVersion?`. 같은 `requestId`는 작업 하나 (`AgentlessRequestHandler`)
- `task.task.requested`: 어느 모듈이든 일을 요청한다. 내용 `requestId, kind, title, instruction?, payload?, targetKind?, targetId?, baseVersion?, agentId?, priority?`. 같은 `requestId`는 작업 하나 (`TaskRequestedHandler`)
- 실행 결과: 내용에 `approvalId`와 `outcome`(`done` · `failed` · `continue`)을 실은 이벤트가 결과다. 실패면 `error`에 이유. `continue`는 승인한 것을 같은 작업이 이어서 한다는 뜻이라 결과를 기다리던 작업(running, 임대 없음)을 다시 대기열로 돌린다 (`Task.continueAfterApproval`, 플러그인 API 0.8, browser-tabs의 누르기 계획). 받는 주제는 `ApprovalResultHandler.TOPICS`(이벤트 목록에서 그 두 칸을 가진 주제 + 기능 패키지의 `plugin.*`)이고, 결과를 담는 주제를 새로 만들면 그 목록에도 더한다 (`approval-result.handler.test.ts`가 이벤트 목록과 맞춰 본다). 두 번 와도 같다

## 써도 되는 모듈
platform. blog의 앱은 platform `Lookups`의 `app`으로만 묻는다 (스토어 2단계, `modules.json`의 lookups.asks)

## 지켜야 할 것
- 상태는 set으로 바꾸지 않는다. 메서드마다 어느 상태에서 올 수 있는지 적는다 (`Task.move(from, to)`): 상태 쌍만 보면 `lease()`가 결재 대기를 가로챌 수 있다
- `.view.ts`는 표 인터페이스(`task.tables.ts`)의 타입만 import한다 (`pnpm check`가 막는다). 웹이 `import type`으로 가져온다
- 주인의 일은 `actor.assertOwner()`로 묻는다. `assertCan(WRITE)`로 물으면 write 권한을 가진 기기가 결재할 수 있다
- 작업 토큰은 저장하지 않는다 (`AgentActor.seal`). `RUN_TOKEN_SECONDS`는 상한이고 실제 끝은 임대다: AI CLI는 받은 토큰을 바꿔 끼울 수 없어 임대가 늘어도 끊기면 안 되고, 끝은 호출마다 `TaskQuery.isLive`가 본다
- 작업 토큰은 `/mcp`에서만 Actor가 된다 (`ActorGuard`, 기기 토큰도 같다). REST에서 쓰면 호출마다 하는 작업 확인을 건너뛴다
- 에이전트에게 `run`을 줄 수 없다. 러너만 일을 빌린다
- 묶인 에이전트(`runner_id`)의 일은 그 러너만 빌린다. 다른 러너가 대신하지 않는다 (꺼져 있으면 기다린다). 칸에는 묶지 않는다. 묶인 에이전트의 칸 일(만들기 · 코드)은 칸이 빌린다 (`Agent.runsOn`, 2026-11-21)
- 결재는 늘 주인에게 (검수 승인을 켠 앱 안의 공개 · 관리자가 대화에서 요청한 앱 배포 · 수정만 원칙 7의 예외)
- 목표는 지우지 않고 상태로 닫는다. 부모는 만들 때 정하고 바꾸지 않는다 (그래서 목표 사슬은 잠그지 않고 읽는다). 진행 중인 목표에만 작업과 하위 목표를 더한다. 목표를 정하는 건 주인이다: AI는 대화에서 바꿀 값을 제안만 하고(설정 바꾸기, 2026-11-15 D) 주인이 승인해야 바뀐다
- 진행 보고는 version을 올리지 않는다 (`saveLease`). 보고가 잦아도 주인의 취소가 막히면 안 된다. 같은 request_id로 다시 보낸 보고도 그 일을 맡았던 러너만 (`assertWorkedBy`)
- 러너가 닿은 때(`RunnerRepository.seen`)도 version을 올리지 않는다: 러너가 자주 닿아도 주인의 켜기·끄기가 막히면 안 된다. `next_jobs` · `report_progress` · `ai_login` · `ai_signin`이 남긴다 (로그인하는 동안 러너는 `ai_signin`만 부른다). 일 받기를 끈 러너의 `next_jobs`는 빈 목록이다
- 잠그는 순서는 어디서나 작업 → 결재 → 외부 도구 → 에이전트. 작업끼리는 위 작업 → 아래 작업 (취소 전파). 위 작업을 깨우는 쪽은 위 작업만 잠근다
- 스케줄: 주기는 매일(시각 + 요일)과 N시간마다만. 시각 계산은 `SchedulePolicy` 한 곳 (크론 라이브러리를 넣지 않는다). 돌리기는 스케줄 → 작업 순서로 쓰고, 작업의 request_id(`schedule:<스케줄>:<시각>`)로 한 번만 만든다. 앞 작업(`schedule:<스케줄>:` 접두어, `hasOpenRequest`) · 가리키는 페이지를 고치는 일(`hasOpenPage`) · 대화의 마지막 회차가 끝나지 않았거나 담당이 일을 받을 수 없으면 건너뛴다. 대화가 아닌 곳으로 보내게 바뀌면 `chat_id`를 비운다 (받을 것을 바꿔도 대화는 그대로, O-4). 앞 레시피를 거슬러 올라가 자기가 나오면(`chainOf`) 고리라 422. 놓친 시각은 몰아서 돌리지 않는다. 담당이 없으면 자동 배정이라 지시가 있어야 한다 (`Schedule` 규칙)
- 하루 한도(`daily_max` 1~288): 스케줄의 시간대 기준 하루에 저절로 만든 작업 수. `run_day`는 글자("YYYY-MM-DD")다: date 칸은 드라이버가 Date로 바꿔 날 비교가 어긋난다. 건너뛴 차례는 세지 않고(`claimRun`은 만들 차례에만), 관리자의 "지금 한 번"은 세지 않고 막지도 않으며 앞 작업도 보지 않는다 (사람이 고른 것, 2026-11-20)
- 주기 (`SchedulePolicy`): 매일(시각 + 요일) · N시간마다(`every_hours` 1~24, 정각 중 시가 N으로 나누어떨어질 때) · N분마다(`every_minutes` 5~720, 시간대 기준 자정부터 N분 간격, 2026-11-20) · 한 번(`once`, `run_at`, 2026-11-27 캘린더: 정한 시각에만, 켤 때 지난 시각이면 거절, `Schedule.fire`가 돈 뒤 끈다). 간격 규칙은 `SchedulePolicy.assertInterval`. 캘린더 `GET api/schedules/calendar`(`ScheduleQuery.calendar`)는 매일 · 한 번의 앞으로 돌 시각(`SchedulePolicy.occurrences`)과 기간 안에 만든 작업 · 회차를 보이고, 화면(자동화 › 스케줄 › 캘린더)에서 날짜를 누르면 그날의 한 번 실행을 등록한다
- 위임: `waiting`에는 늘 기다리는 것(`wait_reason`: approval · subtasks)이 있다 (DB CHECK). 결재 승인 · 고쳐 달라는 말은 결재를 기다리는 작업에만, 깨우기는 하위 작업을 기다리는 작업에만. 받는 쪽 · 종류 · 한도는 `Task`가 막고 LLM에게 맡기지 않는다
- 한도 올리기 결재는 서버만 올린다. 승인은 같은 트랜잭션에서 한도를 두 배로 하고 에이전트를 다시 움직인다
- 쉬기(`Agent.holds`)는 저장하지 않고 그때마다 계산한다. 5시간 토큰이나 구독 사용률에 닿으면 새 일만 안 빌려주고, 달리는 작업은 끝까지 간다. 결재도 `paused`도 없다: `report_progress`가 `paused: true`를 돌려주면 러너가 작업을 돌려주므로 쉬기에는 쓰지 않는다
- 작업 종류는 한 파일 `task-kinds.json`에 적는다 (리팩토링 R3a): 종류마다 필요한 권한(`scopes`) · 스킬(`skill`) · 위임(`delegable`) · 칸(`sandboxed`) · 에이전트 없음(`agentless`). `Task`의 `SCOPES` · `SKILLS` · `DELEGABLE` · `SANDBOXED` · `AGENTLESS`는 이 파일에서 만든다(`TaskKinds`). `task-kinds.test`가 권한 이름(agents.scopes의 값 목록) · 스킬 폴더를, 러너의 `job.test`가 러너가 아는 종류(`Job.KINDS`)가 다 있는지 본다. 종류를 더하면 이 파일 한 줄 + 그 일을 하는 러너 단계 · 스킬
- 작업 토큰의 도구 목록 (2026-11-24, 스토어 3-3): `task-kinds.json`의 `tools`가 있는 종류는 작업 토큰(`AgentActor`의 `tools`, `Task.actorFor` → `TaskKinds.toolsOf`)이 그 MCP 도구만 보고 부른다 (`Actor.mayUseTool`, MCP 입구 `McpEndpoint`가 목록 · 부르기에서 거른다. 권한 · 읽기 허락과 함께 본다). 바깥에서 온 글을 읽는 일(커뮤니티 신고 검토: `community_case` · `propose_setting`)에서 비공개 · 바깥 도구를 닫아, 회원 글의 숨은 지시가 비공개에 닿거나 밖으로 나가지 못하게 한다. 검토 일은 community가 `task.task.requested`로 요청하고 담당은 비어 있다 (대표가 아닌 일꾼 누구나)
- 종류에 꼭 있어야 하는 플러그인은 `task-kinds.json`의 `plugin`(이름 · 러너가 일을 시작하며 부르는 도구)이다 (2026-11-21, `browse` → `browser-tabs`의 `browser_job`). 그 도구가 동작 중인 기능 패키지의 도구(`PluginRegistry.packageTools`)에 없으면 `TaskService`가 만들기(`open`)와 위임(`delegate`)에서 `RuleViolation`("browse 일은 browser-tabs 플러그인이 동작해야 해요")으로 거절한다 (`TaskKinds.assertReady`). 러너가 빌려 가 "browser_job 도구가 없어요"로 실패하던 것을 맡기는 쪽이 까닭과 함께 바로 받는다. 그 전에 쌓인 일은 러너가 실패하며 "설정 › 플러그인에서 browser-tabs를 켜 주세요"를 덧붙인다
- 일의 종류마다 필요한 권한은 `task-kinds.json`의 `scopes`다 (`tidy_session` → `tidy`, `browse` → `browse`, 스킬은 `Task.SKILLS`: `browse` → `moida-browse`). 모든 에이전트가 모든 권한을 가져(2026-11-21) 권한끼리 함께 두지 못하던 규칙(브라우저 · 코드 · 만들기와 비공개 읽기 · 초안)과 비공개를 읽은 대화의 브라우저 위임 금지는 없앴다. `browse`도 위임된다 (2차 3단계, `DELEGABLE`): 대상 `browser_site`면 사이트 일, 없으면 둘러보기. 받는 쪽 · 종류 · 권한의 판단은 `DelegationPolicy` 한 곳이다. `lockNext`가 SQL에서 거르므로 빌렸다가 돌려주지 않고, 맡을 에이전트가 없는 일은 대기열에 남아 뒤의 일을 막지 않는다
- 코드 작업(`code` → 권한 `code`, docs/코드작업.md)은 셸이 있는 코드 러너 칸에서만 돈다 (`Task.SANDBOXED`). 칸인지는 러너가 알리는 값이 아니라 기기의 권한 `sandbox`로 정한다 (`Actor.inSandbox`: 내 컴퓨터 러너가 칸이라고 말해도 받지 못하게). 칸은 `SANDBOXED`만, 다른 러너는 `SANDBOXED`가 아닌 일만 받는다 (`lockNext`). 스킬은 `moida-code`. 위임(`DELEGABLE`에 `code`)은 code 작업에서만: 하위 작업은 위 작업의 저장소 · 명령을 물려받고 `paths`만 위 작업의 경로 안으로 좁힌다. 형제(아직 안 끝난 것 포함)끼리 경로가 겹치면 거절 (`CodeScope`)
- 만들기 작업(`make` → 권한 `make`, 결과물 2차)도 칸에서만 돈다 (`SANDBOXED`). 스킬은 `moida-make`. 위임도 된다 (2026-11-14): 대표가 일꾼에게 `delegate_task`(kind make)로 맡기면 `payload.make`(관리자가 고른 재료)는 물려주지 않는다: 재료를 넘기려면 대표가 대화의 참조를 `refs`로 고른다(`TaskRefs.handOn`, 비공개도 넘긴다 2026-11-21). 페이지 주문(`payload.page`)도 위임에는 없다. 하위 작업이 끝나 깨어난 위 작업에는 그 작업의 결과물(`OutputQuery.madeBy`)이 `subtask_results[].outputs`로 실린다.
  결과를 페이지로 내보내는 주문은 `payload.page`(`PageOrder`, 만들기 일에만): `done`으로 끝낼 때 그 실행의 결과물에 `index.html`이 없으면 작업을 실패로 끝내고, 있으면 `task.page.built`를 남긴다. 페이지가 무엇인지는 blog가 안다 (task는 파일 목록만 싣는다).
  결과를 앱 코드의 새 버전으로 내는 주문은 `payload.appCode`(`AppCodeOrder`, 스토어 1-6, 만들기 일에만, `page`와 함께 적지 않는다: 두 주문의 규칙은 `MakeOrder` 한 곳): `done`으로 끝낼 때 파일이 없거나 한도(100개 · 20MB · 템플릿 1MB)를 넘으면 실패, 아니면 `task.app_code.built`. 한 앱의 코드를 고치는 일은 한 번에 하나 (`tasks_one_open_app_code` → 409). 앱 코드의 나머지 규칙(`moida.json` 등)은 blog가 본다
  재료는 주인이 맡길 때 고른 것뿐이다 (`MakeMaterials`, `payload.make`의 결과물 · 위키 id 각각 10개): 결과물은 맡길 때 살아 있는지 보고(`OutputQuery.liveIds`), 러너는 그 작업의 재료만 `begin_download`로 받는다(`TaskQuery.heldMaterial`).
  위키는 작업 토큰의 읽기 허락으로 준다 (`Task.actorFor`가 `AgentActor`의 `reads`에). 모든 에이전트가 `read_all`을 가져(2026-11-21) 칸 안의 AI도 고르지 않은 위키 · 찾기를 쓴다. 재료 글을 payload에 복사하지 않는다 (비공개 사본이 vault 밖에 남는다). 결재 없이 결과물로 끝난다
- 코드 작업의 겹침(`CodeScope.overlaps`: 같은 저장소, 경로 접두어): 칸이 일을 빌릴 때 공간을 advisory 잠금(`lockCodeLeasing`)하고, 저장소를 쥔 code 작업(도는 중 · PR 결재를 기다림, `Task.holdsCode`. 하위 작업을 기다리는 위 작업은 아님)과 겹치는 일은 건너뛴다. 건너뛸 수 있어 후보를 넉넉히 잠근다 (`CODE_LOOKAHEAD`)
- 쉬는지는 작업을 잠그기 전에 따지고 `lockNext`에서 건너뛴다. 빌렸다가 돌려주지 않는다. 일을 빌릴 때와 `UsageQuery`는 같은 `AgentRepository.usage`를 읽는다
- 초기화 시각이 지난 `plan_usage`는 없는 것과 같다 (`PlanUsage.validAt`). 쉬는 데 쓰지 않고 화면에는 확인 전으로 보인다
- `plan_usage`의 도구는 러너의 입력이 아니라 작업의 에이전트로 정한다. 저장은 에이전트 잠금 뒤에, 늘 같은 창 순서로 (서로 막지 않게). 진행 보고처럼 `task.tasks.version`을 올리지 않는다

- AI 토큰은 REST로 돌려주지 않고 로그에 남기지 않는다. 나가는 길은 `ai_login` 하나고, `run` 권한과 함께 기기인지도 본다 (`AiLoginQuery.token`)
- 웹 로그인(`ai_signin`)도 에이전트·작업 토큰 없이 빌려 주고(`Task.AGENTLESS`), 도구마다 하나다. 러너가 다시 빌리면 단계가 처음(`starting`)으로 돌아간다. 주인이 붙여 넣은 코드는 용도 `ai-signin-code`로 `SecretBox.pack`(10분)해 작업에 두고, 끝날 때까지 물을 때마다 준다 (응답을 잃어도 러너가 다시 받는다). pack은 작업 토큰(`agent-run`)과 열쇠가 같아서 용도가 다르면 풀리지 않게 한다 (`SecretBox`가 용도를 필수로 받는다). 작업 상세에는 암호문도 내보내지 않는다(`Task.shownPayload`). 시작은 공간·도구마다 advisory 잠금(`lockSigninSlot`): 아직 로그인 줄이 없을 수 있어 행을 잠글 수 없다. 러너가 알리는 주소·코드·자격은 믿지 않는 입력이라 `EngineLogin`(엔진 목록의 모양)으로 거르고, 그 작업의 임대를 쥔 러너만 부를 수 있다. 자격을 받으면 같은 트랜잭션에서 로그인을 저장하고 작업을 끝낸다 (작업 → 로그인). `submit_result`의 done은 거절한다. 끝나거나(완료·실패·취소) 대기열로 돌아가면(돌려줌·임대 끝) payload에는 도구만 남긴다. 자격을 넘긴 러너가 다시 보내면 같은 답을 준다(`signinDoneBy`). 로그인하는 동안 러너는 `ai_signin`만 부르므로 여기서도 닿은 때를 남긴다. 주소·코드·자격은 실행 기록에 쓰지 않는다
- 러너는 `next_jobs`로 할 수 있는 것(`tools` · `signin_tools` · `own_logins` · `browser`)을 알리고, 서버가 쓸 수 있는 로그인과 합쳐 그 일만 빌려 준다 (`LeasePolicy`, 에이전트 일은 `ready`를 도구로 거르고 연결 확인 · 웹 로그인은 `lockNext`가 payload의 도구로, 브라우저 작업은 `browser`로 거른다). 갱신 토큰이 바뀌는 도구(엔진 목록의 `login.rotating`: codex)는 서버의 로그인으로 한 번에 하나만 (`canStart`, 한 번의 호출 안에서도)
- `ai_login_refresh`: 바뀌는 자격의 도구만, 그 일을 쥔 러너만, 그 일이 쓴 도구(에이전트의 도구, 에이전트 없는 일은 payload의 도구)만, 받은 판일 때만 (`assertVersion`). 만료와 연결 확인 결과는 두고 자격만 바꾼다(`AiLogin.refresh`). 잠그는 순서는 작업 → 로그인
- Codex의 자격(`auth.json`)은 갱신 토큰이라 만료가 없다 (`expires_at` null)
- 연결 확인(`ai_test`)은 에이전트도 작업 토큰도 없다. 일을 받을 에이전트가 없어도 빌려 주고, 기다리는 확인은 도구마다 하나다. 결과는 작업이 끝날 때 같은 트랜잭션에서 로그인에 적는다 (잠그는 순서는 작업 → 로그인). 작업에 적힌 로그인의 판이 다르면 옛 토큰의 결과라 버린다

- 스킬 판 · 에이전트 설정 판 · 실행 기록은 추가만 한다. 스킬 되돌리기는 `active_revision`만 옮기고, 실행 기록은 비어 있는 `model` · `cli_session` · `resumed`를 러너의 보고로 한 번씩 채우는 것 말고 바꾸지 않는다 (DB 트리거, `TaskRepository.noteRun`). 지시문 글은 실행 기록에 남기지 않는다
- 세션 키 · CLI 세션 재개 (기획서 결정 2026-11-17, `task/run-lineage.policy.ts`): 일을 빌려 줄 때 실행 기록에 세션 키(`lineage`)를 적는다. 대화의 일(회차 · 덧붙인 말의 답 · 검토 · 다시 맡김, `payload.chat.chatId`)은 `chat:<대화>:<에이전트>`, 목표 실행의 회차는 `goal-run:<실행>`, 나머지(하위 작업 포함)는 `task:<작업>`. 에이전트 없는 일과 `task-kinds.json`의 `recorded: false`(세션 정리)는 기록하지 않는다(null). 같은 키의 바로 앞 실행이 같은 러너 · 같은 에이전트 · 같은 설정 판이고 CLI 세션 id를 남겼으면 `next_jobs`의 `run.resume`에 싣는다. 브라우저 · 샌드박스 일은 `run.keep: false`라 재개하지 않는다 (개인정보 규칙 ③, 일마다 지우는 칸). 러너는 세션 파일이 있고 앞 실행이 잘 끝났을 때만 실제로 재개한다
- 작업 점유 시간(lease)은 2분이다 (`Task.LEASE_MS`, 2026-11-17): 러너가 3초마다 `report_progress`로 늘리고, 사라진 러너의 일은 2분 안에 다른 러너가 이어 받는다. 웹 로그인처럼 `report_progress`를 부르지 않는 일은 그 일의 도구(`ai_signin`)가 부를 때마다 늘린다 (`acceptReport`)
- 콘솔에서 고치는 스킬은 러너 스킬(`moida-where: runner`)만. 파일 규칙(경로 · 크기 · 앞부분)은 `SkillFiles`가 막고, 러너도 받은 묶음을 다시 거른다(`apps/runner`의 `SkillPackage`)

- 목표 실행: 회차 작업은 `request_id`(`goal-run:<실행>:<회차>`)로 한 번만 만들고, 작업 쪽에 실행을 가리키는 칸을 두지 않는다 (`GoalRun.runIdOf` · `roundOf`가 읽는다). 회차 작업이 끝나면 `closeRound`가 정한다: 다 됐다는 보고 → 최종 결재(`task.goal.complete`), 결재 시점 · 회차 한도 · 진전 없음 · 보고 없음 · 실패 · 취소 → 중간 결재(`task.goal.continue`), 아니면 다음 회차. 완료는 늘 주인의 최종 승인으로만 (팀장의 "다 됐다"는 주장이다). 승인 · 고쳐 달라는 말은 다음 회차(한도면 한 회차 늘림, 50까지), 거절 · 취소는 멈춤. 기다리는 중이 아니면 결재 이벤트를 무시한다 (두 번 와도 같게). 잠그는 순서는 작업 → 그 작업의 결재 → 실행 → 실행의 결재. 멈추기는 도는 회차 작업과 그 하위 작업 · 결재를 함께 취소한다
- 회차 보고는 AI가 쓴 글이다: 다음 회차의 지시에 실리지만 `read_url`의 기준(주인의 지시)에는 넣지 않는다 (`WebQuery.ownerText`가 실행의 지시를 읽는다). 근거의 주소는 http · https만 받는다 (화면이 링크로 그린다)

- 결과물은 AI가 직접 올리지 않는다: 러너가 일이 끝난 뒤(done) 정해진 폴더의 파일만 올린다. 표는 임대를 쥔 이번 실행만 받고(`TaskQuery.heldRun`), 그 실행 · 이름 · 크기 · sha256에 묶여 10분이다. 본문은 표로만 받는다: AI 토큰은 /mcp에서만 통하고 JSON 한도(512KB)로는 파일을 못 받는다
- 결과물 받기: 트랜잭션 밖에서 파일을 흘려 저장(`BlobStore.saveStream`, 크기 · 해시가 표와 다르면 아무것도 남기지 않음) → 짧은 트랜잭션에서 공간 잠금(`lockSpace`) 뒤 한도(실행 200개 · 1GB, 공간 `MOIDA_OUTPUTS_MAX_GB`, 디스크 여유 `MOIDA_DISK_RESERVE_GB`)를 다시 세고 줄 하나. 같은 실행 · 같은 이름은 한 줄(내용이 다르면 409)
- 결과물 내려받기는 늘 attachment + sandbox CSP. 미리 보기(inline)는 앞부분으로 알아본 그림 · PDF · 영상만: 이름으로 정한 형식(HTML · SVG · 글자)은 우리 주소에서 열지 않는다 HTML(이름이 `.html`)만 예외로 `view=1`일 때 격리해서 연다 (`OutputFile.VIEW_CSP`: AI가 만든 페이지와 같은 sandbox, `allow-same-origin` 없음 → 다른 출처라 로그인 쿠키 · API에 닿지 못한다). 발표 · 표 · 문서를 HTML로 내므로 (moida-make, 2026-11-14)
- 결과물이 가리키는 파일은 `BlobStore.registerUse`로 등록해 둔다 (`OutputQuery.usedBlobs`). 휴지통(30일)을 지나 줄을 지우면 파일은 아무도 쓰지 않을 때 platform이 지운다

## 하지 말 것
- blog·vault·account import. 결재 뒤 실행은 이벤트로 잇는다
- 결재 없이 발행·전송·삭제를 실행하기. 이 모듈은 실행하지 않는다
- 러너의 일을 여기서 하기 (서버 본체에는 AI가 없다)
