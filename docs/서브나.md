## 1. 목적과 다섯 가지 목표

**어디서든 나를 돕는 "서브 나".** 나는 목적을 말하고 결과를 결재만 한다. 일은 서버의 AI 팀이 AI끼리 나눠서 하고, 모든 것은 내 서버 한곳에 남는다.

| # | 목표 | 됐다고 말할 수 있는 때 |
|---|---|---|
| 1 | 내 컴퓨터와 서버가 MCP로 협력해 병렬로 빨리 끝낸다 | Claude Code에서 한 번 맡기면 팀이 서버에서 동시에 일하고, 세션은 묶이지 않고 소식 · 결과를 받는다 |
| 2 | 서버 브라우저로 사이트에서 목적을 이룬다 | 등록한 사이트에서 AI가 양식을 채우고, 결재 뒤 제출까지 되고, 화면 캡처가 남는다 |
| 3 | 모든 AI 작업이 한곳에 모인다 | Claude Code 세션 · 웹 AI 대화 · 서버에서 한 일이 말하지 않아도 서버에 쌓인다 |
| 4 | 글과 결과물을 모아 종류별로 보고, 골라서 블로그로 내보낸다 | 보관함 한 화면에서 결과물 · 읽은 글 · 세션 · 위키를 거르고, 블로그 메뉴로 공개한다 |
| 5 | 새 AI 도구가 나오면 붙여서 자란다 | 새 MCP 도구 · 모델 · CLI를 결재 한 번으로 붙이고, maintainer가 붙일 거리를 PR로 올린다 |

**나에게 오는 것** (콘솔 · 폰에서만. 기기 · AI는 결재하지 못한다):

| 오는 것 | 언제 |
|---|---|
| **결과 결재** | 대화의 일이 끝났을 때. 결과물 · 동작을 골라 승인하면 고른 것만 남고 실행된다 |
| 로그인 필요 | 서버 브라우저가 로그인 화면을 만났을 때. 콘솔 화면에서 로그인하면 이어서 한다 |
| 한도에 닿음 | 회차 · 시간 · 토큰 한도. 그때까지의 최선 결과로 결과 결재가 온다 |
| 도구 붙이기 · 머지 · 배포 | 5번 목표의 결과 결재 (새 도구, maintainer의 PR) |

| 질문 | 새 대화를 맡을 에이전트가 애매할 때만 (2차 1-5). 고르거나 글로 답한다. MCP로 연 대화면 그 세션에도 소식으로 간다. 웹 푸시로도 온다 |
| 답 | 회차의 답이 왔을 때 (웹 푸시, 대화를 열어 보지 않아도) |

일하는 도중의 결재 · 질문은 없다. 팀원은 정해서 진행하고 **가정한 것**을 남긴다. 맡은 에이전트가 모을 때 확인하고 결과 카드에 보인다.

## 3. 화면

**ChatGPT · Claude 같은 대화가 전부다** (2차 1-5, 기획서 결정 2026-11-14). 나는 일이 어떻게 굴러가는지 보지 않고 맡기고 결재한다. 에이전트는 그 뒤의 설정이다.

**① 대화 칸**: 왼쪽에 떠 있는 독(대화 · 일꾼 · 스토어 · 오피스 · 승인 N · 보관함, 아래 알림 · 설정. 폰은 아래 가로 독)이 있고, 그 옆 칸이 새 대화 · 날짜별 대화 목록이다(나에게 온 것 "질문" · "승인"은 채운 표시, 일하는 중은 테두리. 접고 편다). 독의 화면 사이를 오가면 카드가 위아래로 넘어간다 (2026-11-16 떠 있는 콘솔). 가운데는 주고받음 하나와 입력 칸 하나. 팀이 일하는 동안 오른쪽에 "팀이 동시에 일하는 중" 칸: 이 대화에서 시작한 작업마다 맡은 에이전트 · 상태 · 걸린 시간 · 마지막 기록 (넓은 화면에서만).
- 화면의 말은 "결재" 대신 "승인"이다. 이 문서의 "결재"는 화면의 승인과 같다. 아이콘은 선 아이콘 (2026-11-16 테마 B).
- 처음 화면이 새 대화다: 인사 + 입력 하나. 상대 · 프로젝트 · 받을 것 · 목표를 고르지 않는다.
- 입력 칸의 + 단추나 @로 참조를 넣는다 (2026-11-15 B): 보관함에서 찾기 · 주소(서버 브라우저로 열기 고르기) · 파일 올리기(결과물이 된다). 보낸 메시지 아래에 칩으로 남고, 그 회차의 작업만 그것을 읽는다. 새 회차에만 넣는다.
- 대화 머리에서 이 대화의 모델 · 생각 강도를 고른다 (비우면 에이전트의 값). 오른쪽 팀 칸은 서버가 고른 이 대화의 일과 그 아래 작업이다.
- 설정도 대화로 바꾼다 (2026-11-15 C): "리서처 모델을 opus로"라고 하면 대화 상대가 바꿀 칸을 제안하고, 결과 카드에 "모델: sonnet → opus"가 뜬다(권한을 더하는 줄은 굵게). 승인하면 서버가 바꾼다. 에이전트 · 스케줄(C)에 더해 목표 · 블로그 메뉴 · 사이트 이름과 소개 · 알림 · 세션 정리 · 프로젝트별 모으기 · 플러그인 설정(D). AI 계정 · 비밀값 · 계정 · 보안 · 기기 · 사이트 주소 · 플러그인 켜고 끄기 · 스킬 · 지우기는 화면에서.
- "이 버그 고쳐 줘"는 코드 작업 열기 요청이 된다: 승인하면 그 저장소의 코드 작업이 열리고, PR이 나오면 머지 승인을 한 번 더 받는다.
- 보내면 **배정**: 맡는 일(에이전트 역할의 첫 줄)이 맞는 에이전트가 맡는다. 후보가 하나면 바로, 여럿이면 AI가 한 번 고르고(배정 일), 애매하면 대화에 질문과 고를 것이 뜬다. 고르거나 글로 답한다.
- 일하는 동안은 답 위에 접힌 한 줄(일하는 중 · 소식 N개)만. 펼치면 팀이 남긴 소식(정한 것 · 가정 · 팀원 끝남)과 작업.
- 끝나면 답 아래 결과 카드. 결재함에도 보이지만 고르는 것은 대화에서만.
- 같은 대화가 MCP로도 열린다: `ask_agent`에 상대를 생략하면 같은 배정, 질문은 `agent_updates`로 간다(고를 것과 함께). 웹과 그 세션 어느 쪽에서 답해도 된다. 결재는 콘솔 · 폰에서만.

**② 팀 · 설정**: "팀"은 에이전트 카드(도구 · 모델 · 생각 강도 · 보고 대상 · 지금 상태 · 권한 칩 · 사용량)와 조직도 · 팀 템플릿 · 휴지통. 제품의 핵심 설정이라 설정과 따로 둔다. "설정"은 AI 계정 · 사이트 · 알림 · 계정 · 보안(로그인한 곳 · 기기의 마지막 접근 · 보안 기록)만 펼쳐 두고, 나머지(목표 · 스케줄 · 작업 기록 · 세션 · 위키 · 지식 그래프 · 글 · 블로그 메뉴 · 커넥터 · 러너 · 연결된 기기 · 플러그인 · 스킬 · MCP 도구 설명 · 오피스, 기능 패키지 메뉴)는 접힌 "고급"에 둔다. 설정은 대화에서 제안 → 승인으로 바꾸는 쪽으로 옮겨 가고(설정 바꾸기 제안), 화면은 대화가 만든 것을 보고 다듬는 곳이다.

**③ 보관함**: 결과물 · 읽은 웹 글 · 블로그 글 · 세션 · 위키를 한 화면에서, 종류 · 프로젝트로 거른다 (5단계).

## 4. 대화와 AI 팀

> 2026-11-21: 팀(보고 라인 · 팀장 · 팀 템플릿)은 없앴다. 관리자는 대표 하나와 이야기하고, 대표는 작은 일을 직접 하며 큰 일만 모두 같은 일꾼에게 나눠 맡긴다 (기획서 결정 기록). 아래의 "팀"은 일꾼들로 읽는다.

| 역할 | 하는 일 |
|---|---|
| 맡은 에이전트 (팀장) | 배정으로 대화를 맡는다. 받을 것에서 거꾸로 계획하고 팀원에게 나눠 맡긴다. 모아서 결론을 쓰고 결과 결재를 올린다 |
| 실행 담당 | 리서처(웹 검색 · `read_url`) · 분석가 · 제작자(샌드박스, HTML) · 브라우저 담당(서버 브라우저) · 코드 담당 |
| 검토자 | 기준표로 점수를 매기고 반론한다. 만든 쪽과 다른 도구(Claude ↔ Codex) |
| 판정 | 받을 것의 검사. 하네스와 서버가 한다 (AI의 "다 됐다"는 주장이다) |

- **상태판**: 대화마다 목표 · 받을 것 · 정한 것 · 가정한 것 · 시도 기록. 메시지는 종류(제안 · 반론 · 결정 · 가정 · 결과)를 단다.
- **소식**: 팀원 끝남 · 중간 보고 · 가정 · 최종 결과. 내 세션은 훅(말을 걸 때마다) + 상태 줄로 받는다. 채널(push)은 켤 수 있을 때.
- **멈춤**: 대화마다 한도(기본 회차 10 · 2시간 · 토큰). 점수가 두 번 연속 오르지 않으면 최선안으로 결과 결재를 올린다.
- **퍼지지 않게**: AI의 말은 서로에게 자료다. 지시는 내가 쓴 말뿐이다. 내 세션(기기)의 말은 기기의 말로 남아 `read_url`의 기준을 넓히지 않는다.

## 5. 결과 결재와 받을 것

대화를 시작할 때 끝에 받을 것 하나를 정한다. 기본은 세션 · 대표가 요청을 보고 고르고, 세부 모양(보고서 · 표 · 발표 · 지도)과 가는 길은 AI가 정한다.

| 받을 것 | 어디까지 | 검사 |
|---|---|---|
| HTML | 보관함 | `index.html`, 필수 구성, 근거의 출처 링크 |
| 블로그 | 메뉴 · 호에 올리고 공개 대기 | 글 발행 · 호 발행 결재가 있는지, 메뉴에 올리지 않은 글 · 빈 호 (ActionChecks). 편집 방침 · 쓴 재료는 검토자 짝이 본다 |
| 브라우저 동작 | 마지막 클릭 직전 | 허용 출처 안에서만 움직였는지, 결재된 클릭이 준비됐는지 |
| 코드 (저장소 프로젝트) | `moida/<작업>` 브랜치 | `pnpm check` · 테스트 |
| (안 정함) 대화 답 | 말풍선 | 없음 |

**결과 결재 카드**: 항목(결과물 · 동작)마다 고르는 칸, 수정 요청 메모, 승인(고른 개수) · 수정 요청 · 반려.
- 승인: 고른 결과물은 보관함에 남고 고르지 않은 것은 휴지통으로. 고른 동작은 실행한다 (발행은 서버가, 브라우저 제출은 결재된 클릭으로).
- 수정 요청: 메모가 대표에게 가고 같은 대화의 다음 회차로.
- 반려: 모두 거절.

**검증 고리 (V, 2026-11-16)**: 사람에게 가기 전에 기계가 아는 실패는 AI가 한 번 고친다. 모두 횟수 한도가 있고, 넘으면 떨어진 채로 카드에 보인다.
- 러너 검사(코드의 `checks`, 만들기의 결과물 · `index.html`)가 떨어지면 같은 작업 폴더에서 AI를 한 번 더 (틀 `check-fix`). 결과의 `checks`가 카드 항목 옆에 보인다.
- 받을 것이 결과에 없으면 다시 맡김 (2번, 틀 `result-check`).
- 검토자 짝은 판정(그대로 승인 · 고칠 것 있음 · 반려 권함)과 완료 조건 체크리스트를 JSON으로 낸다. 끝난 회차가 "고칠 것 있음"이면 같은 상대에게 한 번 다시 맡기고(틀 `result-fix`) 다시 검토한다. 결재만 기다리는 회차는 다시 맡기지 않고 판정과 고칠 것을 카드에 싣는다 (수정 요청 메모에 미리 채움).
- 카드: 판정 · 체크리스트 · 항목별 검사 · 자동으로 고친 횟수. 고르지 말라는 항목은 처음부터 풀어 둔다. 다시 맡긴 회차가 같은 이름으로 다시 낸 결과물은 마지막 것만 싣는다.

## 6. 러너와 하네스

| 러너 | 셸 | AI가 도는 동안 바깥 | 맡는 일 |
|---|---|---|---|
| 일반 러너 (서버, 동시 N, 기본 3) | 없음 | 일반 인터넷 + 서버 브라우저 | 조사 · 글 · 대화 · 검토 · 브라우저 일 |
| 샌드박스 러너 (서버, 칸 하나에 일 하나) | 있음 | 모델 API + 서버만 | 코드 · 만들기 · 페이지 고치기 |
| maintainer (샌드박스의 코드 에이전트, 7단계) | 있음 | 샌드박스의 허용 목록 (GitHub · npm, 따로 망은 필요해지면) | Moida 자신 · CLI · 스킬 · 확장의 최신화. PR까지 ([정비](정비.md)) |
| 내 컴퓨터 러너 (선택) | 없음 | 내 네트워크 | 묶인 에이전트의 일만. 내 폴더 복사본 |

- 하네스: ① 빌리기 → ② 준비(AI 없음) → ③ AI → ④ 끝(검사 · push · 결과물 · 기억 메모 · 제출, AI 없음) → ⑤ 치우기. ④의 검사가 떨어지면 ③을 한 번 더 (검증 고리 V).
- 맴돎 멈추기 (2026-11-28): ③에서 같은 도구 부름이 같은 결과를 4번 · 같은 오류를 3번 · 두 동작을 번갈아 6번 내면 하네스가 AI를 끄고 "맴돌아 멈췄어요"로 실패로 끝낸다 (입력 · 결과는 해시로만 본다). 대표는 먼저 깨어 다른 길로 맡기고, 깰 때마다 진행 장부(`note_progress`: 끝났나 · 나아지나 · 맴도나 · 다음)를 남긴다. 진전 없음이 3번 이어지면 계획(단계)을 다시 세운다 (완료 조건은 그대로).
- 셸과 자유로운 인터넷을 한 러너에 두지 않는다. 셸과 비공개도. 비밀은 하네스 메모리에만. 결과는 서버에 두고 내 세션이 가져간다.
- 화면 이름 "칸"은 "샌드박스"로 바꾼다.

## 7. 서버 브라우저: AI 팀의 손발

- **기본 손발**: 서버 브라우저는 늘 켜져 있다. 브라우저 담당(일반 러너 + Playwright MCP)이 등록한 사이트의 허용 출처 안에서 일한다. 브라우저 담당은 비공개를 읽지 않는다.
- **보기 · 로그인 · 직접 하기**: 콘솔 화면(HTTPS). 누르고 바로 입력, 한글 · 붙여 넣기 · 키 · 휠 (구현됨).
- **로그인**: 비밀번호는 어디에도 저장하지 않는다. 내가 콘솔 화면에서 한 번 로그인하고(2단계 인증 포함) 브라우저는 로그인 상태만 기억한다. 세션이 끊기면 "로그인 필요" 결재 → 콘솔 화면에서 로그인 → "로그인했어요" → 같은 작업이 이어서 한다 (위임 사슬은 끊기지 않는다). 사이트마다 "세션 지우기"(그 사이트의 쿠키 · 저장소만 지움). 자동화용 계정을 권한다. 브라우저의 비밀번호 저장은 정책으로 꺼져 있다.
- **둘러보기 모드**: 로그인이 필요 없는 조사 · 가격 비교는 일마다 새 빈 컨텍스트로 아무 공개 사이트나. 로그인된 프로필은 건드리지 않고, 이 서버 · 내부망 주소는 러너의 프록시가 막는다. 여럿이 함께 돈다 (사이트 일은 러너마다 하나씩).
- **단계 캡처**: 일의 단계마다 화면을 작업에 남긴다 (결과물이 아니라 `browser-tabs`에: 작업마다 30장 · 30일). 멈춘 화면 · 누른 뒤 화면은 클릭 카드에서 본다.
- **결재된 클릭**: AI는 마지막 버튼(제출 · 결제 · 게시) 앞에서 멈추고 "어느 페이지의 어느 버튼"을 남긴다. 하네스(AI 없음)가 그 버튼을 다시 찾아 지문 · 그때의 화면과 함께 붙잡아 결재를 올린다 (AI는 결재를 올리지 않는다). 결과 결재에서 승인하면 하네스가 같은 탭 · 같은 페이지 · 같은 버튼인지 확인하고 누른 뒤 결과 화면을 남긴다. 페이지가 바뀌었으면 누르지 않고 "콘솔 화면에서 직접"으로 돌린다.
- **위임**: 대표는 `delegate_task`(kind `browse`)로 브라우저 담당에게 맡긴다. 맡기는 쪽도 전체 읽기 · 초안 작성이 없어야 한다 (비공개가 지시를 타고 바깥 사이트로 가지 않게). 비공개를 읽는 대표는 맡기지 못하고 관리자가 브라우저 메뉴에서 맡긴다.
- **Mac AI 브라우저**: 서버 IP가 막히는 사이트, 사내망이 필요할 때만 쓰는 보조 (7단계에서 필요하면).

## 8. 모으기와 기억

- **Claude Code 세션** (4단계 구현): `moida connect`가 세션 저장 기기(OAuth `scope=collect`, 권한 `upload`만)를 만들고 `SessionEnd` 훅(`~/.moida/bin/moida-collect.mjs`)을 건다. 훅은 떼어 낸 프로세스로 원문(사람 말 · AI 말 · 도구 이름만, 도구 입출력 · 생각은 뺌)을 만들어 민감정보를 지운 뒤 `save_transcript`로 올린다. 못 올린 것은 `~/.moida/outbox/`에 두었다가 다음 훅에서 다시(200개까지). 저장소의 `.moida.json`에 `"collect": false`면 올리지 않는다. `moida status`에 마지막 저장 · 기다리는 수.
- **원문 → 노트** (4단계 구현): vault가 원문(`session_transcripts`, 추가만)을 쌓으면 노트 없는 세션이 먼저 보이고, 세션 노트 일(`session_note`)이 생긴다. 서버 러너가 에이전트 없이 서버의 로그인으로 돌린다: 일을 쥔 뒤 원문을 받아(`read_transcript`, 앞 4만 · 뒤 8만 자) 틀 `session-note`로 쓰고 답(JSON)을 `save_note`로 보내면 vault가 노트(원본 판)로 쌓는다. 원문은 작업 · 이벤트에 싣지 않는다. 관리자는 세션 화면에서 원문을 보고, 프로젝트마다 모으기를 끈다(`api/project-rules`).
- **소식 · 상태 줄**: `moida connect`가 소식 기기(권한 `news`, 읽기만)를 만들고 훅 · 상태 줄을 깐다. 이미 있는 훅 · 상태 줄은 덮지 않는다.
- **브라우저 확장 (내 브라우저, `apps/extension`, 4단계 구현)**: 보고 모으기만. 확장 기기(OAuth `scope=extension`, 돌려받는 주소 `https://<확장 id>.chromiumapp.org/`, 권한 `upload` · `delegate` · `inbox`). 정한 사이트(ChatGPT · Claude · Gemini 웹 대화, 사이트마다 켜고 끔)는 화면이 20초 조용해지면 `save_transcript`로, "이 페이지 보관"은 소재 링크로(`keep_page`, 읽은 글은 메모), "이 페이지로 맡기기"는 `ask_agent`로 대화를, 아이콘의 숫자는 1분마다 `inbox`(기다리는 결재 · 질문). 방문 기록 전체는 모으지 않고 클릭하지 않는다. 사이트별 읽는 부분(`src/capture/<사이트>.js`)은 maintainer가 점검한다.
- **기억**: 맡길 때 관련 위키를 붙인다(`moida-recall`). 어시스턴트마다 "일마다 새로 / 앞 일의 메모 이어 받기"(`remember`).

## 9. 보관함 · 자라는 페이지 · 블로그 · 자동화

- **보관함** (구현, `GET /api/library`): 결과물 · 페이지 · 읽은 웹 글(탭 읽기 · 확장) · 블로그 글 · 세션 · 위키를 한 화면에. 종류 · 프로젝트(세션) · 기간으로 거른다. 새 표 없이 모듈마다 자기 읽기를 platform에 등록한다. 여기서 블로그에 올리는 것은 6단계.
- **자라는 페이지** (구현): 계속 쓸 결과물(여행지도 · 현황판). `index.html` + `data.json`, 방향(나만 고침), 판(추가만), 바뀐 점(데이터 차이), 고치기는 한 번에 하나. 고치는 일은 지금 판의 글 파일을 받아(`page_base`) 바뀐 파일만 낸다. 공개 페이지의 새 판은 확인 대기 + 즉시 알림, 관리자가 미리 보고 "이 버전 보이기".
- **블로그** (구현, `api/menus` · `api/issues`): 하나의 블로그에 메뉴(글 목록 · 호 목록 · 페이지 모음 · 페이지 하나, `/m/<주소>`). 올리기(보관함 · `blog_save_draft`의 `menu_id`) → 공개 두 단계. 메뉴마다 편집 방침 · 운영 팀(비공개를 읽지 않는 에이전트) · RSS. 매거진은 호 단위, 발행은 호 전체를 한 번에(`blog.issue.publish`).
- **자동화** (구현, 스케줄을 넓혀): 레시피(언제 · 누가 · 무엇을 · 받을 것 · 어디로 · 지킬 것). 어디로는 작업 · 대화(담당의 대화 회차, 결과는 결과 카드로) · 페이지(새 판). 계기는 정한 시각 · 손 · 다른 레시피 끝남. GitHub 계기는 8단계(연동).

## 10. 성장: 새 AI 도구 붙이기

| 붙일 것 | 길 |
|---|---|
| 스킬 · 작업 방식 | 콘솔 스킬 메뉴 (1차에서 됨) |
| 모델 · 생각 강도 (구현) | 에이전트 편집의 "모델" · "생각 강도" (`agents.model` · `effort`). 비우면 CLI의 기본. 강도는 도구가 받는 값만 (Claude low~max, Codex low~high). 일과 함께 러너에게 가서 Claude는 `--model` · `--effort`, Codex는 설정 파일로 |
| MCP 도구 (새 서비스, 구현) | **도구 꽂기** (`task.external_tools`, 설정 › 외부 도구): 원격(https) MCP만. 관리자가 더하면 바로, AI는 `propose_tool`로 제안 → 결과 카드의 `task.tool.plug` 승인 → 켜지고 제안한 에이전트에 붙는다. 에이전트마다 허락하고(`agents.external_tools`), 러너가 그 에이전트의 일에만 `x-<이름>`으로 붙인다. 비공개를 읽거나(`read_all` · `write`) 셸이 있는(`code` · `make`) 에이전트에는 붙이지 않는다. 토큰은 서버 키로 잠그고 화면 · AI · 로그에 다시 나오지 않는다 |
| AI CLI (예: Gemini CLI, 계약 구현) | 러너 어댑터 + 계약 시험(`apps/runner/src/ai-tool.test.ts`)을 모든 도구가 통과한다. 새 도구 · 새 버전은 maintainer가 [정비](정비.md) 순서로 PR |
| maintainer (구현) | 팀 템플릿 `maintainer`: 점검 담당(셸 없음)이 매주 레시피로 CLI 새 버전 · 바뀐 점을 찾아 "코드 맡기기" 지시문을 내고, 관리자가 코드 메뉴에서 정비 개발자에게 맡기면 PR. 순서는 [정비](정비.md) |
| 정리 (구현) | 세션 정리: 기본 하루 한 번 몰아서(`tidy_settings.cadence`, 일꾼 `TidyDailyJob`), 저장마다도 고를 수 있다. 위키 점검: 팀 템플릿 `tidy`의 위키 점검 담당에게 매주 레시피. 연결 더하기는 바로, 대체 · 분류 · 공개 전환은 검토 (`submit_changes`의 규칙 그대로). 보관함 점검은 쓰지 않는 결과물을 알아볼 신호가 없어 하지 않는다 |

## 12. 지키는 것

- 원칙 1~7 그대로 ([AGENTS.md](../AGENTS.md)). 위험한 동작은 결과 결재 뒤에 믿는 코드가 실행한다. AI가 직접 발행 · 전송 · 삭제 · 제출하지 않는다.
- 비밀번호는 저장하지 않는다. 비밀(GitHub 토큰 · AI 로그인)은 하네스 메모리에만.
- 브라우저 담당 · 둘러보기 · 셸이 있는 러너에게 비공개를 주지 않는다.
- 내 브라우저에서 AI는 클릭하지 않는다 (확장은 보고 모으기만).
- 조종 포트(CDP)는 밖으로 열지 않는다. 서버 브라우저 화면은 관리자만.

## 13. 바뀌는 1차 결정

## 14. 대표 · 결과물 · 대화로 자동화 (2026-11-18 승인)

실제로 써 보니 대화를 맡은 팀장 하나는 자기 팀(바로 아래)에게만 맡길 수 있어서, 그 팀에 없는 능력(예: 초안 저장 `write`)이 필요하면 "화면에서 권한을 바꿔 주세요"로 끝났다. 사용자는 대표와만 이야기하고, 결과물로 받고, 반복할 일은 대화로 자동화를 걸고 싶다 (사용자 요청 2026-11-18).

1. **대표는 일마다 새로 뜨고, 조직도는 그대로.** 대표는 숨은 시스템 에이전트 하나다 (팀 화면 · 조직도에 없음). 대화 · 자동화 실행 · MCP `ask_agent`를 모두 대표가 받고, 대화 상대 고르기 · 배정 일(`chat_route`) · 배정 질문은 지운다. 대화마다 대표가 따로 뜨고(같은 대화는 CLI 세션 재개로 이어 감) 다른 대화끼리는 동시에 일한다 (한 에이전트의 동시 일을 막는 규칙은 없다). 지금 맨 위 에이전트(팀장)들은 그대로 맨 위이고, 대표는 그 위에서 누구에게나 맡긴다. 대표는 비공개를 읽지 않고 글도 쓰지 않는다(나누고 모으고 제안만): 대표가 비공개를 읽으면 브라우저 팀에 쓰는 지시를 타고 바깥으로 나간다. 모델 · 도구는 설정 › AI. 설정 바꾸기 제안은 대표만 (대화를 맡던 팀장의 권한이 대표로 옮겨 간다).
2. **알아서 하게.** 대표는 맨 위 에이전트마다 그 팀 전체가 할 수 있는 일(일의 종류 · 커넥터)을 보고 고른다. 할 수 있는 팀이 없으면 반드시 결과 카드에 제안(권한 더하기 · 에이전트 만들기)을 올리고, 승인하면 서버가 같은 대화를 이어서 열어 원래 일을 마저 한다.
3. **결과물로 이야기.** 대표는 첫 실행에서 받을 것(글 초안 · 파일 · 페이지 · 앱 코드 · 브라우저 · 코드 · 자동화 · 답)을 정하고, 서버는 결과 카드에 그것이 있는지 본다 (없으면 다시 맡김, 지금의 받을 것 검사를 넓힘). 답 글은 두세 줄, 화면의 중심은 결과 카드, 과정은 접힘. 질문에는 짧은 답이 결과물이다.
4. **대화로 자동화.** "매일 아침 ~해 줘"면 대표가 자동화(스케줄) 등록을 결과 카드에 올린다 (지금의 `propose_setting schedule`, 맡는 쪽은 대표, 결과는 대화로). 돌 때마다 대표가 새로 떠서 팀에 맡기고 결과는 그 자동화의 대화에 카드로 쌓인다. 발행 · 전송은 매번 승인 (원칙 7). 멈추기 · 바꾸기도 대화로.
5. **토큰 보기.** 대화 머리에 합계, 답마다 과정에 이번 답의 합계와 에이전트별, 대화 목록에 합계. 수는 설정 › AI 한도와 같은 기준.
6. **지키는 것.** 비공개를 읽는 에이전트가 이미 일한 회차에서는 브라우저 일을 맡기지 못한다 (대표가 비공개 결과를 받아 브라우저 팀에 넘기는 길을 막음. 2026-11-21에 없앴다: 모두 비공개를 읽는 같은 일꾼). 권한을 더하는 제안은 승인 뒤에만.

고르지 않은 것: 대표를 에이전트 없이(agentless) 돌리기 (위임 · 작업 토큰 · 한도 · 실행 기록이 모두 에이전트를 전제로 해 크게 고쳐야 함), 대표를 조직도 맨 위의 보이는 에이전트로 (기존 팀을 모두 옮겨야 함), 답 글을 아예 없애기 (질문형 요청).

O-1에서 정한 것: 토큰은 표를 더하지 않고 `task_events.tokens`를 읽을 때 모은다 (회차 `chat:<대화>:<회차>…` · 배정 `chat-route:<대화>:`과 그 아래 하위 작업, 회차는 맨 위 작업의 request_id 세 번째 칸). 일하는 동안의 늘어남은 이미 오는 신호(`task.event.added`)로 다시 읽는다. 러너의 브라우저는 `next_jobs`가 마지막으로 알린 값 또는 쥔 실행 중인 브라우저 작업이다 (사이트 일이 도는 동안 러너는 거짓을 알린다. 일하는 동안에는 next_jobs를 부르지 않아 시각으로는 판단하지 않는다). `chat.view.ts`가 300줄이라 MCP 소식 도구의 모양(`agent_updates` · `post_update`)을 `chat-update.view.ts`로 나눴다.

O-2에서 정한 것: 대표는 `agents.lead`(공간마다 하나, 부분 유일 색인 `agents_one_lead`, `CHECK (NOT lead OR reports_to IS NULL)`)인 보통 에이전트 줄이다. 마이그레이션이 에이전트가 있는 공간마다 하나 만들고(도구는 서버에 로그인이 있는 것, claude 먼저), 새 공간은 첫 대화에서 서버가 만든다(`AgentEdit.lead`, advisory 잠금). 이름 · 역할 · 권한(`read_public`)은 서버가 정하고 관리자는 설정 › AI에서 AI 도구 · 모델 · 생각 강도 · 한도 · 검토자만 바꾼다(`AgentLead`). 목록 · 조직도 · `get_settings team` · 다른 모듈의 카드에 보이지 않고, 아무도 대표에게 보고하지 않으며 지울 수 없다. 담당 없는 일을 자동 배정할 때도 대표는 고르지 않는다 (대화만 맡는다). 대표는 맨 위 에이전트 전부를 팀원으로 보고(`Agent.manages`), 팀원 정보의 아래 팀 요약은 손자 팀까지 사람 · 일의 종류 · 커넥터 수다(이름 없음, 모든 팀장에게 같은 규칙). 설정 바꾸기 · 코드 작업 열기를 승인 동작 없이 올리는 것은 맨 위 에이전트가 아니라 대표만이다. 브라우저 일은 대화 단위로 막는다: 그 대화(대화가 아니면 맨 위 작업의 나무)에 비공개를 읽는 에이전트의 작업이 있었거나 비공개 참조가 있으면 누구도 브라우저 일을 맡기지 못한다(`TaskRepository.privateTouched`). 승인 뒤 이어서는 `propose_setting`의 `continue`(대표만, 결재 `payload.continue`)이고, 설정이 적용되어 그 결재를 기다리던 회차가 끝나면(`task.task.changed` done) `ChatContinueHandler`가 같은 대화에 회차 하나를 연다(지시문 틀 `setting-continue`, `fixBy: setting`, 결재마다 한 번). 적용 결과 이벤트가 아니라 작업의 끝을 받는 까닭: 결과 이벤트를 받는 쪽이 둘이라 회차가 아직 끝나기 전일 수 있다. 배정 일 · 질문 · `task.chat.asked` 알림은 지웠다 (O-2 전의 기록은 그대로 보인다). O-2 전에 맡기 전이던 대화는 다음 말에서 대표가 맡는다. 알림 설정에 저장된, 지금은 없는 종류의 경로는 저장할 때 버린다(platform `NoticeSettings`).

O-3에서 정한 것: 받을 것은 회차마다 대표가 첫 실행에서 정한다(MCP `set_deliver`, 작업 토큰, 대표의 대화 회차만). 값은 맨 위 회차 작업의 `payload.chat.deliver` · `deliverNote`에 적고(표를 더하지 않는다), 검사는 그 값 · 없으면 대화의 값(`chats.deliver`, 관리자 · 레시피)을 본다(`TurnDeliver`). 대화의 값이 있으면 대표는 그 값만 정할 수 있고(원칙 3), 한 회차에 한 번 정한다. 목록은 `answer`(짧은 답, 검사 없음) · `file`(결과물 하나 이상) · `html` · `app_code`(`blog.app_code.show`) · `blog` · `browser` · `code` · `setting`(`task.setting.change`)으로 넓혔다 (마이그레이션은 CHECK만, `ChatResult.NEEDS` 한 줄씩). 서버가 연 회차(검사 · 검토 반영 · 승인 뒤 이어서)는 `payload.chat.note`에 화면용 한 줄을 남기고 작업 제목도 그 한 줄이며, 앞 회차의 받을 것을 물려받는다(`Chat.fix`). 대화에서 올라온 결재로 만든 대화 레시피는 승인할 때 그 대화에 묶이고(`Schedule.bindChat`, `approvals.chat_id`), 묶인 레시피의 회차는 레시피의 받을 것을 싣는다. `get_settings schedules`에 `chat_id`, 상세에 `automations`. 구현하며 찾은 것: 대표의 회차가 자기 승인 요청을 기다리다 카드에서 승인되어 끝나면 실을 것이 0이라 받을 것이 빠져 보여 다시 맡기던 문제 → 이 회차가 실린 카드를 이미 정했으면 다시 맡기지 않는다(`ApprovalRepository.cardDecided`). 화면: 회차마다 받을 것 칩(까닭은 마우스를 올리면), 결과물을 내는 회차의 긴 답은 세 줄까지 접고 "펼치기"(서버는 자르지 않는다), 서버가 연 회차의 말풍선은 한 줄과 짧은 머리(검사 · 검토 반영 · 승인 뒤 이어서), 대화 머리에 "자동화 · 매일 08:00 · 평일" 칩(스케줄 화면으로). `ChatDetailView.question`과 `agent_updates`의 `choices`는 지웠다 (`chat_updates.choices` 칸은 기록이라 둔다).

O-4에서 정한 것: 자동화(대화 레시피)의 받을 것은 대화 칸(`chats.deliver`)이 아니라 회차마다 싣는다 (처음 여는 대화도 `Chat.assign(…, deliver)`). 그래서 레시피의 받을 것을 바꿔도 묶인 대화를 놓지 않고, 다음 회차부터 새 받을 것을 싣는다. 대화가 아닌 곳으로 보내게 바뀔 때만 대화를 놓는다 (다시 대화로 보내면 다음 차례에 새 대화). O-2에서 담당은 늘 비어 있어(대표) 담당이 바뀌어 놓는 경우는 없어졌다.
