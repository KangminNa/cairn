# Moida 테이블 설계

> 칼럼의 원본은 `db/migrations/`이고, 코드는 `apps/server/src/modules/<모듈>/<모듈>.tables.ts` · `<모듈>.schema.ts`(`pnpm db:rows`가 생성)로 표를 안다. 표의 주인은 `apps/server/modules.json`.
> 이 문서에는 코드만 봐서는 모를 뜻과 규칙만 둔다. "아직 안 씀"은 표는 있지만 쓰는 코드가 없다는 뜻이다.

## 0. 공통 규칙

| 항목 | 규칙 |
|---|---|
| DB | Postgres 17, 확장 `pg_bigm`(한국어 키워드), `pgcrypto`. 이미지는 pgvector 이미지라 `vector` 확장이 깔려 있지만 쓰는 표는 없다 (이미지를 바꿀 때 뺀다) |
| 스키마 | **모듈 = 스키마.** `platform`(공통 기반), `account`(공간·사람·기기·로그인), `vault`(세션·그래프·변경 묶음), `blog`·`work`(글과 소재, blog 모듈 소유), `task`(에이전트·작업·결재), `mcp`(도구의 글) |
| 모듈 사이 | **외래키를 두지 않는다.** 다른 모듈의 행을 가리키는 열(`space_id`, `device_id`, `blob_hash` 등)은 값만 갖고, 유효성은 주인 모듈의 코드가 지킨다. `pnpm db:check`가 막는다 |
| 기본키 | UUIDv7. 시간순이라 B-tree 끝에만 쌓여 쓰기에 유리하다. 앱에서 만들고 `platform.uuid_v7()`은 예비용이다. 로그 표는 `bigint` |
| 공간 | 사용자 데이터 표는 모두 `space_id`를 가진다. 지금은 공간 하나. 복합 인덱스는 `space_id`를 맨 앞에 둔다 |
| 삭제 | 사용자 데이터는 `deleted_at` + `purge_after`(휴지통) |
| 낙관적 잠금 | 사람이 고치는 행에 `version` |
| 행위자 | `actor_type`(`user`·`device`·`ai`·`system`) + `actor_id`. 사람이 읽는 표기는 화면에서 조립한다 |
| 열거형 | 자주 늘어날 종류는 목록 표(`node_kinds`, `edge_kinds`), 거의 안 바뀌는 상태값은 `text + CHECK` |
| 확장 열 | 주요 엔티티의 `meta`. 새 도구의 추가 정보, 복원한 md의 모르는 앞부분 키를 둔다 |
| 추가만 하는 표 | `session_revisions`, `session_transcripts`, `wiki_revisions`, `post_revisions`, `task_events`, `skill_revisions`, `tool_text_revisions`, `agent_revisions`, `task_runs`(비어 있는 `model` · `cli_session` · `resumed`를 한 번씩 채우는 것만 된다), `run_memos`. 트리거 `platform.forbid_update_delete()`가 UPDATE·DELETE를 막는다. 영구 삭제 일꾼만 `SET LOCAL moida.allow_purge = 'on'`으로 지나간다 |

**문서를 저장하는 세 겹** (세션·wiki·글)

| 겹 | 열 | 역할 |
|---|---|---|
| 원문 | `body_md` | 원본. 내보내면 그대로 .md 파일이 된다 |
| 쪼갠 칸 | `sections`, `section_hashes` | 칸 단위 합치기, 화면 표시, 차이 비교 |
| 찾기용 복사본 | `head_*`와 검색 색인 | 목록·검색을 빠르게. 지금 판이 바뀔 때 같은 트랜잭션에서 고친다 |

판은 추가만 하고, 지금 보여줄 판은 부모 행의 `head_revision_id`와 `version`으로 가리킨다. 판 추가·포인터 갱신·일 임대·사람 우선 검사를 한 트랜잭션에 묶어야 하고 관계 규칙이 많아서 문서 DB가 아니라 Postgres를 쓴다.

## 1. 늘어날 자리

지금 쓰는 모양이 나중에도 버티는 까닭이다. 쓰지 않는 표 · 칸은 미리 두지 않는다 (2026-11-14에 임베딩 · 첨부 · 편집 임대 · 공감 기록 · 이메일 칸 등을 지웠다. 필요해지는 단계에서 그때의 모양으로 다시 만든다).

| 나중에 생길 일 | 지금 모양 | 그때 할 일 |
|---|---|---|
| 팀 블로그, 공식 호스팅 | 모든 데이터에 `space_id`, `space_members.role` | 공간 추가, 행 수준 보안 켜기 |
| 새 점·연결 종류 | `node_kinds`, `edge_kinds` | 목록에 행 추가 (점은 상세 표도 하나) |
| 세션 노트 칸 변경 | 판마다 `sections_schema` | 새 파서 추가, 옛 판은 그대로 |
| 그래프 보기 여러 개 | `graph_views.settings`, `node_layout(view_id, node_id)` | 보기 행 추가. 설정이 늘어도 열을 늘리지 않는다 |
| 로그가 수억 건 | 시각 BRIN + 날짜 기준 삭제 (1인 블로그는 수백만 행도 충분) | 그때 월별 분할 |

## 2. `account` · `platform` · `mcp`

**account**

- `spaces`: 블로그 하나. 설치됐다 = 주인이 있다. 설치 코드는 서버 키에서 만들고 저장하지 않는다. `logo_blob_hash`는 사이트 로고 파일(platform.blobs의 해시, 값으로만, CHECK로 sha256 모양)이다. 파일 청소에서 지키려고 `BlobStore.registerUse`에 등록한다.
- `users`: `login`이 아이디다. `password_hash`는 `scrypt$N$r$p$salt$hash`이고 원문은 어디에도 두지 않는다. `display_name`(1~40자, 비면 화면은 아이디)은 화면에서 "주인" 대신 보일 이름이고, 이것을 고칠 때만 `version`이 오른다 (로그인 · 비밀번호 저장은 올리지 않는다, 2026-11-14).
- `login_links`: 로그인 플러그인으로 들어온 외부 계정과 주인의 연결. 여기에 연결된 계정으로만 주인 로그인이 된다.
- `space_members`: 공간마다 `owner` 한 명 (부분 유일 인덱스).
- `settings`: 값은 `blog.description`, `site.url`, `connect.hosted_apps`. 비밀값은 플러그인 설정(`platform.plugin_settings.secret_ciphertext`)과 AI 로그인(`task.ai_logins`)에만 서버 키로 잠가 둔다.
- `devices`: 기기는 지우지 않고 `revoked_at`으로 끊는다 (다른 모듈이 id를 값으로 갖고 있다). 이름은 끊지 않은 기기 사이에서만 겹치지 않으면 된다. 권한 `sandbox`는 코드 러너 칸 기기만 갖고, 그 기기는 `run` · `sandbox`만 갖는다 (CHECK `devices_sandbox_only`). 권한 `delegate`(에이전트에게 맡기기, 2026-11-14)는 관리자가 켜고, 그 기기의 AI 도구가 MCP로 서버 팀에 메시지를 보낸다. 권한 `news`(소식 읽기, 2차 1-3)는 앱이 승인 요청에 `scope=news`를 실어 만든 소식 기기만 갖고, 그 기기는 `news`만 갖는다 (CHECK `devices_news_only`, 관리자도 바꾸지 못한다). 권한 `inbox`(결재 · 질문 보기, 2차 4단계)는 브라우저 확장 기기가 갖고 관리자도 줄 수 있다. 앱이 요청한 기기 모양(`news` · `collect` · `extension`)은 승인 코드의 `oauth_codes.device_draft.scopes`에 실려 기기를 만들 때 그 모양의 권한이 된다 (`Device.PROFILES`). `is_primary_tidy`는 아직 안 씀.
- `oauth_codes`: 5분, 한 번만. 기기는 코드를 토큰으로 바꿀 때 `device_draft`로 만든다 (그만둔 승인이 남지 않게).
- `oauth_tokens`, `device_tokens`, `web_sessions`: 토큰은 해시만 저장한다. `web_sessions.last_seen_at` · `last_ip`와 `devices.last_seen_at` · `last_ip`는 마지막 접근이다 (보안 화면, 2026-11-15): Guard가 알아본 요청에서 Service가 프로세스마다 5분에 한 번만 적고 version은 올리지 않는다. 로그인의 마지막 접근을 적을 때 `web_sessions.expires_at`도 그때부터 30일로 늘린다 (마지막으로 쓴 날부터 30일, 웹 UX U2 2026-11-19. 이미 끝난 로그인은 늘리지 않는다). 주소는 `inet`이라 IP 모양이 아니면 적지 않는다.

**platform**

- `blobs`: 기본키가 내용의 sha256이다. `blog.assets`, `blog.posts.cover_blob_hash`, `work.basket_items`(그리고 `task.outputs`, `blog.page_revisions.files`, `blog.app_code_versions.files`)가 값으로 가리키고, 도메인끼리는 서로를 모른다. 외래키가 없어 DB가 지켜 주지 않으므로, 가리키는 모듈이 `BlobStore.registerUse`로 "이 해시들 중 쓰는 것"을 등록하고 `BlobSweepJob`이 아무도 쓰지 않는 7일 지난 파일만 지운다. `created_at`은 마지막으로 저장한 때다 (다시 저장하면 새로 되어 지우기 기다림이 처음부터).
- `idempotency`: 같은 요청은 처음 결과를 돌려준다. `device_id`는 이름과 달리 호출한 쪽의 값이다: 기기, 주인, 작업 토큰이면 작업, 결재한 공개면 공간.
- `outbox`: 일꾼이 빌릴 때 `next_attempt_at`을 뒤로 미뤄 다른 일꾼이 잡지 않게 한다. 실패하면 `last_error`, 8번 실패하면 `failed_at`을 찍고 멈춘다 (지우지 않고 남겨 원인을 본다). 멈출 때 같은 트랜잭션에서 관리자에게 알리고(`platform.event.failed`), 관리자가 설정 › 일 › 처리 실패 · `pnpm run events retry`로 다시 시도하면 `attempts` 0 · `failed_at` NULL · `next_attempt_at` 지금으로 돌린다 (리팩토링 R1). `trace_id`: 이벤트를 남긴 요청의 번호(`X-Request-Id`), 일꾼이 그 번호로 로그를 남기고 거기서 남긴 이벤트에도 잇는다 (요청 밖이면 그 실행의 번호, 모르면 NULL). `outbox_failed_idx`(공간 · `failed_at` 내림차순, 멈춘 것만): 처리 실패 목록.
- `plugins`, `plugin_settings`: 설정은 DB에 둔다. `granted_uses`는 켤 때 주인이 허락한 확장 지점이다. 값은 `value`나 `secret_ciphertext` 중 하나만 있다.
- `notifications`: 알리는 모듈이 자기 트랜잭션에서 `Notices`로 쓴다. 대부분은 모듈이 등록한 종류(`NoticeCatalog`)대로 이벤트와 같은 트랜잭션에서 생긴다 (`Outbox.listen`). 같은 `group_key`의 안 읽은 알림이 있으면 새로 쌓지 않고 바꾸고, 그때 `push_sent_at`을 비워 다시 보낼 차례가 된다. 경로가 `off`인 종류는 쌓지 않는다. 콘솔 머리줄의 알림이 읽고 읽음으로 바꾸고, 끝난 일의 알림은 모듈이 정한 이벤트에서 읽음이 된다(`Notices.settle`). `push_sent_at`은 "푸시를 다룬 때"다: 보냈거나, 보내지 않기로 했거나(경로가 알림 센터만 · 하루 지남).
- `notice_settings`: 공간마다 한 줄, 없으면 기본값 (묶음은 매시, 조용한 시간 없음, UTC). 묶음 간격(`digest` hourly · daily + `digest_minute`), 조용한 시간(`quiet_start` · `quiet_end`, 시간대 기준 하루 중 분, 둘은 함께 비거나 함께 찬다), 시간대, 종류별 경로(`routes`: 종류 → push · center · off, 없는 종류는 등급의 기본), 종류별 메일(`mail`: 종류 → on · off, 없는 종류는 종류의 기본: 대화의 답은 끔 · 나머지는 켬, 경로가 push일 때만 메일 플러그인으로도 간다, 2026-11-27).
- `security_events`: 보안 기록 (2026-11-15). 로그인 성공 · 실패 · 막힘, 로그아웃 · 로그인 끝내기, 비밀번호 바꿈, 설치 코드 틀림, 기기 연결 · 해제 · 갱신 토큰 재사용, 러너 연결, 거부된 접근(`/api` · `/mcp` · `/oauth`의 401 · 403 · 429, 401은 토큰 · 쿠키를 내민 것만). platform이 갖고 종류의 뜻은 기록하는 모듈이 정한다 (`SecurityLog`). 같은 공간 · 종류 · 곳(`place`: IPv4, IPv6는 /64) · 내용(`detail`)이 1분 안에 또 오면 줄을 늘리지 않고 `count` · `last_at`만 올린다. `space_id`가 NULL이면 공간을 모르는 사건(없는 아이디로 로그인, 로그인 전 거부)이다. 비밀번호 · 토큰 · 쿠키 값은 두지 않고, 틀린 아이디는 관리자의 것일 때만 적는다. 90일 지나면 일꾼이 지운다 (`SecurityLogPurgeJob`). 인덱스: 목록 `(at DESC, id DESC)`, 1분 안의 같은 사건 찾기 `(kind, place, last_at)`.
- `push_subscriptions`: 브라우저 하나에 한 줄 (`endpoint` 유일, 알려진 푸시 서비스의 https 주소만). 받는 쪽 키(`p256dh` · `auth`), 공간(`space_id`), 연속 실패 수(`fail_count`, 다섯 번이면 지움)와 마지막 성공. 보내는 쪽 키(VAPID)는 표에 없고 서버 키에서 만든다. `embedding_models`: 의미 검색 때 쓴다 (아직 안 씀).

**mcp**: `tool_texts` + `tool_text_revisions`(추가만)는 MCP 도구의 글을 콘솔에서 고친 판이다 (2차 1-0): 공간 · 도구마다 한 줄(`(space_id, tool)` 유일)이 지금 쓰는 판(`active_revision`, 비면 기본 글)을 가리키고, 판은 설명(1~4,000자) · 칸 설명(`input`: 칸 경로 → 글, 빠진 칸은 기본 글) · 고칠 때 기본 글의 해시(`based_on`) · 메모를 남긴다. 기본 글은 표가 아니라 코드 밖 설명서(`<모듈>.tools.ko.json`)와 기능 패키지의 목록 파일이다

## 3. `vault`

### 그래프 = 대표 하나 + 선

| 점 | 대표 (열 하나) | 비어 있으면 |
|---|---|---|
| 세션 | `sessions.wiki_id` | 도착 구역 (정리 전) |
| wiki | `wikis.category_id` | 미분류 |
| 글 (blog) | `posts.main_wiki_id` (값). vault는 사본 `post_marks.main_wiki_id`로 안다 | 그래프에 나오지 않음 |

- 대표가 하나라는 규칙을 DB 구조로 지킨다. 옮기기·합치기는 대표 값 하나를 바꾸는 일이라, 카테고리를 바꿔도 바뀌는 행이 wiki 몇 개로 끝난다.
- "미분류"와 "도착 구역"은 행이 아니라 `NULL`이다. 지우거나 이름을 바꿀 수 없다.
- 대표 밖 연결은 `edges`의 선이다: `material`(세션 → 다른 wiki), `link`(wiki ↔ wiki), `replaces`(새 wiki → 결론이 뒤집힌 옛 wiki, [wiki 점수](wiki점수.md). 옛 wiki 하나에 하나만: `edges_replaced_once`), `similar`(계산값, 아직 안 씀). 글 → 다른 wiki는 `blog.post_wiki_refs`.
- 부모를 지워도 자식은 지워지지 않는다. 카테고리를 영구 삭제하려면 먼저 wiki를 옮겨야 하고(`RESTRICT`), wiki가 영구 삭제되면 세션은 도착 구역으로 간다(`SET NULL`). `CASCADE`는 같은 점의 일부(상세 행, 판, 그 점의 선, 검색 조각)에만 쓴다.

### 세션과 wiki

- `nodes`: 세션·카테고리·wiki를 한 표로 묶어 선이 외래키 하나로 걸리게 한다. 글은 점 표에 없다.
- `sessions`: 대화 하나가 `(space_id, device_id, tool, source_session_id)`다. `pinned_sections`는 사람이 고친 칸이고, 칸 이름 말고 `#title`(wiki 제목), `#wiki`(세션의 대표 wiki)도 들어간다. `tidy_requested_seq`는 정리를 요청한 마지막 판이다: `revision_count`보다 뒤처진 세션만 고르고, 실패한 세션은 새 판이 쌓여야 다시 고른다. 이 값을 적어도 세션 `version`은 오르지 않는다. `settled_seq`(S2, 2026-11-28)는 작업 세션(도구 `moida-agent`)에서 요청이 완료로 끝난 때의 판 번호다: 작업 세션은 `revision_count` 대신 이 번호까지만 정리하고(취소 · 실패 · 반려된 요청은 원문으로만), 사람의 세션은 쓰지 않는다. 이 값도 `version`을 올리지 않는다. `held_revision_id`는 편집 중이라 보류한 새 원본이다 (아직 안 씀).
- `session_revisions`: `kind`는 `origin`(AI 도구 · 서버 러너의 세션 노트), `human`, `merge`. `redactions`는 지운 민감정보 표시다. 서버 러너가 원문으로 쓴 노트는 `actor_type` `ai`(만든 쪽 id 없음).
- `session_transcripts` (2차 4단계, 추가만): 수집 훅 · 확장이 올린 대화 원문(민감정보를 지운 것, 1,000,000자). `UNIQUE (session_id, content_hash)`로 같은 원문은 한 번, `seq`는 세션 안의 번호. 원문이 먼저 오는 세션은 노트(판)가 없는 채로 있다 (`head_revision_id` NULL). `sessions.transcript_count`는 쌓인 원문 수, `sessions.noted_seq`는 지금 노트를 쓴 원문의 번호(늦게 온 옛 원문의 노트가 새 노트를 덮지 않게). 원문은 작업 · 이벤트에 복사하지 않는다 (러너가 `read_transcript`로 받아 간다). 보관 형식에는 `vault/transcripts/<세션 id>/<번호>.md`로 쌓인 그대로 나간다 ([보관 형식](보관형식.md))
- 작업 세션 (2026-11-17, 기획서 결정 "에이전트 실행의 기록은 작업 세션이다"): 에이전트의 요청 하나(대화 · 목표 실행 · 맨 위 작업)가 `sessions` 한 줄이다. `tool = 'moida-agent'`, `source_session_id`는 task가 정한 작업 세션 키(`chat:<대화>` · `goal-run:<실행>` · `task:<맨 위 작업>`)이고, 러너 기기와 상관없이 하나라서 부분 유일 색인 `sessions_agent_flow (space_id, source_session_id) WHERE tool = 'moida-agent'`이 지킨다. 기기의 저장은 이 도구 이름을 쓰지 못한다. 실행마다 원문 한 줄(`session_transcripts`, `actor_type` device: 머리 · 원문 · 인수인계 메모, 비밀값을 지우고 개인정보를 마스킹한 것)과 노트 판(`actor_type` system: 최근 메모 20개를 이어 붙인 것, AI 없음)이 쌓인다. 판이 쌓여도 `vault.session.saved`를 내지 않고(자동 정리 · 세션 알림 없음) 정리 대상에서도 뺀다 (끝난 요청의 정리는 S2)
- `run_memos` (2026-11-17, 추가만): 인수인계 메모 한 줄 = 에이전트 실행 하나. `session_id`(작업 세션) · `transcript_seq`(그 실행의 원문 번호, 세션 안에서 유일) · `lineage`(세션 키) · `task_id` · `run_seq`(task의 `task_runs.seq`, `(task_id, run_seq)` 유일) · `agent_id` · `agent_name` · `task_title` · `memo`(4,000자) · `written_by`(`ai`: AI가 메모 파일에 씀, `runner`: 못 써서 러너가 대신 만듦). `task_id` · `agent_id`는 task 모듈의 값이라 외래키가 없다. 같은 세션 키의 다음 실행이 `run_memos` 도구로 최근 5개를 받는다(색인 `(space_id, lineage, created_at DESC)`, 휴지통 세션의 것은 빼고). 보관 형식에는 따로 나가지 않는다: 메모는 원문 안에 있다
- `categories`: `description`은 분류 기준이고 정리 스킬이 읽는다.
- `wiki_revisions`: `kind`는 `ai`, `human`, `merge`. 칸은 md 제목(`##`) 단위다. `base_revision_id`는 보고 고친 판, `change_set_id`는 나온 묶음이다.
- `wiki_aliases`: 합쳐져 없어진 wiki의 옛 주소. 글의 참고가 깨지지 않게 한다. `old_id`는 영구 삭제됐을 수 있어 외래키가 없다 (대정리, 아직 안 씀).
- `edges`: 방향 없는 종류는 `src < dst`로 정렬해 저장한다. 사람이 지운 연결은 행을 남겨(`deleted_at`, `deleted_by_type`) AI가 다시 만들지 못한다.
- `post_marks`: 글 자리 사본. vault는 blog를 읽지 않으므로, blog의 글 이벤트를 Handler가 받아 적고 그래프는 이것으로 글 점과 선을 그린다. 이벤트 순서가 바뀌어도 `post_version`이 큰 것만 반영한다. `status`는 `draft`·`published`뿐이라 링크만 공개는 `draft`로 적는다. `app_id`(스토어 1-2)는 글이 든 앱 (글 이벤트의 `appId`, 외래키 없음).
- `app_marks` (스토어 1-2): 앱 공개 여부 사본 `(app_id, space_id, public, app_version)`. `blog.app.changed`를 받아 적고, `app_version`이 더 큰 것만 반영한다. 지운 앱은 `public = false`로 남겨 늦게 온 이벤트가 되살리지 못하게 한다. 방문자 그래프는 `post_marks`와 이어 앱도 공개인 글만 그린다 (사본이 없거나 앱 밖의 글은 숨긴다). 앱을 비공개로 바꾸면 이 표의 한 줄만 바뀐다. 마이그레이션이 그때의 `blog.apps` · `blog.posts`로 한 번 채웠다 (vault가 다른 스키마를 읽은 것은 이 한 번뿐). 복원은 보관 파일의 앱 파일로 채우고, 앱이 생기기 전의 백업은 기본 앱(id = 공간 id) 하나로 채운다
- `stale_wikis`: 지울 만한 wiki로 이미 알린 것 ([wiki 점수](wiki점수.md) 7장). 6시간마다 일꾼이 지금 후보와 맞춰 새 후보만 알리고, 후보에서 빠지면 줄을 지운다. 지우는 것은 주인이다.
- `tidy_settings`: 행이 없으면 자동 정리 꺼짐. `cadence`(save · daily, 기본 daily, 2차 7단계): daily면 저장 때 요청하지 않고 일꾼 `TidyDailyJob`이 하루 한 번(`daily_at`에서 23시간 뒤) 새 판이 쌓인 세션을 요청한다. `project_rules`: 프로젝트별 수집 여부 `collect`(2차 4단계, 줄이 없으면 모은다. 끄면 그 프로젝트의 원문을 쌓지 않는다. `api/project-rules`가 늘 덮어쓴다)와 기본 공개(아직 안 씀).
- `graph_views`: 방문자·주인의 기본 보기와 저장한 보기. `audience`마다 기본은 하나다. `settings`는 서버의 `GraphView`가 읽을 자리고, `node_layout`의 좌표는 보기마다 있다. 지금은 보관 파일만 고정한 점을 읽는다.

### 변경 묶음

git처럼 다룬다: 결과 한 번 = 묶음(커밋) 하나, 승인함 = 검토를 기다리는 `change_ops`(PR), 대정리 = 작성 중인 묶음(브랜치), 되돌리기 = 새 묶음(revert). 관리 화면 편집도 묶음(`human`)으로 남기되 규칙은 거치지 않는다. 그래서 승인함·되돌리기·기록을 두 번 만들지 않는다.

- `change_sets`: `kind`는 `tidy`, `reorg`(대정리), `human`, `revert`, `system`. `status`의 `open`은 대정리 작성 중, `review`는 검토 대기다. `job_id`는 작업 id를 값으로 담고 유일해서 정리 결과의 중복 적용을 막는다: 러너가 `submit_changes`와 `submit_result` 사이에 죽어도 두 번째 제출은 첫 묶음을 돌려준다.
- `change_ops`: 요청한 일 하나. `op`는 서버의 `ChangeOp` 이름이다. `base_version`은 판정할 때 대상의 version이고, 승인할 때 어긋나면 `superseded`가 된다.
- `changes`: 실제로 바뀐 행의 `before`·`after`. `batch_id`는 묶음 id이고 되돌리기 단위다. `domain` CHECK에 옛 값 `app`이 남아 있다.
- `review_rules`: 주인이 고른 값만 둔다. 규칙의 뜻은 서버의 `ReviewPolicy`에 있고, 행이 없으면 기본값이다.

## 4. `blog`

- `apps` (스토어 1단계, [스토어](스토어.md) 8장): 앱 하나. `kind`(blog · magazine · page, 만들 때만), `slug`(바깥 주소 `/<slug>`, 영어 소문자 · 숫자 · 하이픈 2~30자, 공간 안에서 하나, 못 쓰는 이름은 코드의 `App.RESERVED`), `visibility`(private 기본 · public), `sort`, `description`(200자), `icon_blob_hash`(BlobStore.registerUse). 설정이라 판이 없고 글 · 페이지 · 호가 없어야 지운다(빈 메뉴는 함께). 방문자에게 글 · 메뉴 · 호 · 페이지 · 사진이 보이려면 앱도 공개여야 한다 (각 Query의 방문자 조건). 마이그레이션이 지금 블로그를 기본 앱 하나(`blog`, 공개)로 옮겼다. 순서 색인 `apps_order_idx`는 앱 목록 · 공개 앱 아이콘 목록용.
- `apps`의 운영 칸 (스토어 2단계, [스토어](스토어.md) 10장): `agent_id`(운영 팀장, task의 맨 위 에이전트 id. 값이라 외래키 없음, 지운 에이전트도 비우지 않아 휴지통에서 되살리면 그대로) · `policy`(편집 방침 4000자) · `home`(방문자 첫 화면 고정, `apps_home_public` CHECK로 공개 앱만, 부분 유일 색인 `apps_one_home`으로 공간마다 하나). 운영 팀은 팀장과 그 아래 팀 전체이고 판단은 blog의 `AppTeam`이 한다.
- `apps`의 도메인 칸 (스토어 3-0, [스토어](스토어.md) 11.4): `domain`(앱 도메인, 소문자 · 국제 도메인은 `xn--` 꼴, 모양 CHECK `apps_domain_format`, 모든 공간에서 하나 `apps_domain_key`: 요청의 Host로 앱을 찾을 때도 이 색인을 쓴다) · `domain_checked_at`(관리자의 브라우저가 그 도메인의 확인 값을 읽어 온 때, 도메인을 바꾸면 비운다, CHECK `apps_domain_checked`). 확인한 도메인이어야 기본 도메인의 앱 주소가 그리로 보낸다. 보관 형식에는 넣지 않는다 (배포마다의 값).
- `apps.code_manifest` (앱 플랫폼, [스토어](스토어.md) 12.1): 보이는 버전의 선언서(`moida.json`)를 정리한 모양(jsonb: `render` · `hosts` · `members` · `permissions` · `theme` · `tables`). 보이는 버전이 바뀔 때 함께 바뀐다. 회원을 받는 앱인지(`members`)와 화면의 권한을 여기서 읽는다
- `apps`의 코드 칸 (스토어 1-6, [스토어](스토어.md) 9장): `code_seq`(방문자에게 보이는 버전, NULL이면 종류의 시작 코드) · `code_pending_seq`(공개 앱의 확인 대기 버전) · `code_versions`(쌓인 버전 수). 버전을 바꾸면 `apps.version`이 오른다 (앱 설정과 같은 줄이라 낙관적 잠금 하나).
- `app_code_versions` (스토어 1-6): 앱 코드의 버전. 추가만 한다 (트리거). `files`는 페이지 판과 같은 모양(`[{ name, blobHash, mime, sizeBytes }]`, 100개 · 폴더 없음 · `index.html`이 꼭 있다, 합쳐 20MB · 템플릿 `.html`은 1MB)이고 버전마다 묶음 전체다 (AI 작업은 앞 버전 · 시작 코드 위에 바꾼 파일을 얹는다). `source`(starter · upload · task · restore: 백업의 `blog/apps/<주소>/code/`에서 들어온 버전 1, 스토어 1-6c), `task_id` · `run_id`는 task의 값(`source = 'task'`일 때만, CHECK)이고 `UNIQUE(app_id, run_id)`로 같은 이벤트를 두 번 받아도 버전은 하나다. `app_id`는 외래키 없는 값이다: 버전이 추가만이라 외래키를 걸면 코드를 고친 앱을 지울 수 없다 (앱을 지워도 버전은 남는다, 원칙 2). 파일은 `BlobStore.registerUse`(`blog.app_code_versions.files`)로 지킨다.
- `app_id`: 메뉴는 늘 앱 하나에(NOT NULL, 주소는 앱 안에서 하나 `menus_app_id_slug_key`), 글 · 페이지는 NULL이면 앱 밖(글은 공개 · 링크만으로 바꿀 수 없다: CHECK `posts_shown_in_app`, 페이지는 지금처럼 `/pages/<이름>/`). 메뉴에 올린 글 · 페이지는 그 메뉴의 앱에 든다 (`(menu_id, app_id)` → `menus(id, app_id)` 외래키). 색인 `posts_app_public_idx`는 앱 첫 화면의 공개 글 목록, `pages_app_idx`는 앱에 든 페이지.
- `posts`: `status`는 `draft`(임시) · `published`(공개) · `unlisted`(링크만). `title`은 지금 판의 찾기용 사본이다. `slug`는 한글을 허용하고 기본값은 제목에서 만든다. `main_wiki_id`는 vault의 값이라 외래키가 없다.
- `post_revisions`: 제목·본문이 바뀔 때만 판을 쌓는다. 주소·태그·정렬·공개 범위는 글에 둔다. `blocks`는 아직 안 씀.
- `post_wiki_refs`: 글이 대표 말고 참고한 wiki. 글의 출처는 이것으로만 남기고 세션은 wiki를 거쳐 안다.
- `assets`: 글 ↔ 파일. 사진의 공개 여부는 파일이 아니라 붙은 글로 정한다.
- `pages`: AI가 만든 HTML 묶음 하나 (2026-11-12). `name`은 주소(`/pages/<name>/`)로 공간 안에서 하나이고, 처음 제목에서 만든 뒤 바뀌지 않는다 (겹치면 뒤에 번호). `visibility`는 `private`(기본, 주인만) · `public`. `current_seq`는 지금 보이는 판, `revisions`는 쌓인 판 수 (`current_seq <= revisions`). 자라는 페이지(2차 5단계): `direction`은 관리자만 고치는 쓰임(4000자, 새 판을 만드는 AI가 지시와 함께 읽는다), `pending_seq`는 공개 페이지에 붙었지만 아직 보이지 않는 판(확인 대기, `1..revisions`, 보이면 비운다).
- `page_revisions`: 추가만 한다 (트리거). 판 하나 = 작업 한 번의 실행이 만든 파일 묶음. `files`는 `[{ name, blobHash, mime, sizeBytes }]` (100개까지, 하위 폴더 없음, `index.html`이 꼭 있다. 있는 페이지의 새 판은 앞 판의 파일 위에 이번 파일을 얹은 전체다). 판의 `data.json`은 화면의 "바뀐 점"(앞 판과의 차이)에 쓰인다. `task_id` · `run_id`는 task의 값이라 외래키가 없고, `UNIQUE(page_id, run_id)`로 같은 이벤트를 두 번 받아도 판은 하나다. `note`는 그 판을 만든 요청 글.
- `menus` (2차 6단계, 쓰지 않던 `categories`를 바꿔 넓힘): 공개 블로그 메뉴 줄의 한 칸. `kind`(posts · issues · pages · page, 만들 때만), `slug`(앱 안에서 하나, `/<앱>/m/<slug>`, 스토어 1단계), `sort`, `policy`(편집 방침 4000자), `agent_id`(운영 팀, task의 값이라 외래키 없음), `rss`. 설정이라 판이 없고 안이 비어야 지운다.
- `posts.menu_id`(쓰지 않던 `category_id`) · `pages.menu_id`: 올린 메뉴. 올린 것은 공개 대기이고 보이는 것은 공개 범위가 정한다. 글은 메뉴와 호 중 하나에만(CHECK `posts_menu_or_issue`).
- `issues` (2차 6단계, 쓰지 않던 `series`): 호 목록 메뉴 안의 호. `(menu_id, number)` 유일, `status`(draft · published, 발행이면 `published_at` · CHECK), `title`, `intro`, `version`. 글은 `posts.issue_id` · `issue_order`(쓰지 않던 `series_id` · `series_order`)로 순서대로 든다. 발행은 호와 글을 한 트랜잭션에 모두.

## 5. `work`

blog 모듈이 가진 스키마다.

- `baskets`: 공간마다 기본 상자 하나. 처음 담을 때 만든다.
- `basket_items`: 소재 하나. `kind`마다 필요한 칸을 CHECK가 정한다. `ref_id`는 세션·글의 값이라 외래키가 없다. 사진·파일은 표에 있지만 올리는 길이 없어 받지 않는다.

## 6. `task`

에이전트, 작업, 결재. 대기열이 둘이 되지 않게 정리 일도 `tasks`에 함께 둔다.

- 모듈 사이 외래키는 없다. `space_id`, `leased_by`, `decided_by`, `target_id`, `runners.device_id`는 값으로만 가리킨다. 모듈 안(`tasks.agent_id`, `approvals.task_id`, `goals.parent_id`, `tasks.goal_id`, `schedules.agent_id` · `goal_id` · `after_id` · `chat_id`, `goal_runs.goal_id` · `agent_id`, `goal_rounds.run_id`, `chats.agent_id`, `agents.runner_id`)은 외래키를 둔다.
- `agents.deleted_at`: 휴지통 (2026-11-14). 차 있으면 목록 · 일 빌리기(`usage`) · 위임에서 빠지고, `AgentRepository.load` · `lock`은 없는 것으로 본다. 작업 · 실행 기록 · 설정 판이 외래키로 가리켜 줄을 지우지 않으므로 `purge_after`가 없다. 지울 때 팀원은 지운 에이전트의 보고 대상으로 올라간다 (같은 저장에서 `reports_to` · `settings_revision`).
- `agents.reports_to`: 지웠다 (2026-11-21, 팀 없는 같은 일꾼). 보고 라인 · 팀장이 없고, 대표만 일꾼에게 맡긴다. 권한끼리 섞지 못하게 막던 CHECK(`agents_browse_not_private` · `code` · `make` · `tools_not_private` · `pinned_not_sandboxed` · `lead_top` · `reports_to_self`)도 함께 지웠다. 마이그레이션은 모든 에이전트에게 권한 전부와 사이트 클릭 · 로그인 승인 동작을 준다
- `goals`: 목표 나무 (맨 위가 회사 목표, 5단계까지). 지우지 않고 `done`·`dropped`로 닫는다. 부모는 만들 때 정하고 바꾸지 않아서, 목표 사슬은 잠그지 않고 재귀 CTE로 읽는다. 작업은 진행 중인 목표에만 잇는다 (`tasks.goal_id`).
- `agents.lead`: 공간의 대표 (O-2, 2026-11-18). 모든 대화 · 대화로 보내는 스케줄 · `ask_agent`를 받는 숨은 에이전트. 공간마다 하나(부분 유일 색인 `agents_one_lead`: `lead AND deleted_at IS NULL`). 권한은 `read_public`, 이름 · 역할은 서버가 정한다. 마이그레이션이 에이전트가 있던 공간마다 하나 만들고(도구는 서버에 로그인이 있는 것), 새 공간은 첫 대화에서 만든다. 맡은 대화(`chats.agent_id`)는 대표로 옮기고, 대화로 보내는 스케줄의 담당은 비웠다(대표가 맡는다). 기다리던 배정 일(`chat_route`)은 취소했다
- `agents.reviewer_id`: 검토자 짝 (2차 2단계). 이 에이전트와 나눈 대화의 회차가 끝나면 결과 카드 전에 검토 작업을 맡는다. 같은 표, 자기 자신은 CHECK `agents_reviewer_other`, 같은 AI 도구는 `Agent.pairReviewer`가 막는다.
- `agents.reviewer_approves` (2026-11-20 검수): 대표만 켠다. 켜면 대화의 일에서 올라온 앱 안의 공개(글 · 앱 화면)를 검토자 짝이 먼저 검수하고 통과면 대신 승인한다 (`ChatInspect`). 검토자를 떼면 함께 꺼진다 (`Agent.pairReviewer`).
- `agents.second_inspector_id` (2026-11-20 두 검수자, 선택): 대표만. 검수 승인이 켜졌을 때 이 에이전트도 같은 결재를 따로 검수하고 둘 다 통과해야 승인한다. 대표 · 검토자가 아니고 검토자와 다른 AI 도구 (`AgentLead.assertSecond`). 검토자를 떼면 함께 빠진다.
- `agents.preset` (2026-11-28 역할 일꾼): 역할 일꾼의 열쇠(`task/agent-roles.json`: planner · researcher · writer · maker · developer · reviewer · browser). null이면 예전 일꾼. 공간마다 살아 있는 것 하나(`agents_one_preset` 부분 유일 색인), 대표에는 없다(CHECK `agents_preset_not_lead`). 서버가 만들고(`AgentRoster`) 이름 · 역할은 정의 파일 그대로다.
- `verdicts` (2026-11-20 평가가 남는 팀, 추가만 · 트리거 `platform.forbid_update_delete`): 검토 · 검수 작업 하나가 끝나면 판정받은 에이전트마다 한 줄 (`UNIQUE(task_id, agent_id)`). 판정(`pass` · `fix` · `reject` · `unknown`) · 완료 조건 점수의 평균(`score` real 1~5) · 가장 낮은 점수(`low`) · 같은 대상의 몇 번째 판정(`round`) · 대상 열쇠(`target`: 검수는 `inspect:<대화>:<동작>:<대상>`, 검토는 `review:<대화>:<처음 회차>`). 판정받은 에이전트는 검수면 결재를 올린 에이전트, 검토면 그 회차의 바로 아래 하위 작업 에이전트들(없으면 대표). 성적표(`AgentRepository.scores`: 첫 판정 통과 · 평균 고친 횟수)와 검수의 "점수가 오르지 않음"(`VerdictRepository.lastScore`)이 읽는다. 색인: 에이전트 · 기간(`verdicts_agent_idx`), 대상(`verdicts_target_idx`).
- `learned_rules` (2026-11-28 배운 규칙, ACE): 피드백에서 배운 규칙 한 줄. 공간 안의 번호 `seq`(지시문의 R<seq>, `UNIQUE(space_id, seq)`, 공간마다 advisory 잠금 뒤 가장 큰 번호 + 1) · 대상 `scope`(all · role · app)과 `scope_key`(role은 역할 키 `agents.preset`, app은 앱 id, all은 null, CHECK) · 글 `body`(1~300자) · 도움 `helpful` · 해로움 `harmful` · 상태 `status`(active · retired, 내리면 `retired_at`, CHECK) · 만든 근거 `approval_id`(승인한 제안) · 고치기 · 합치기로 내렸으면 새 규칙 `replaced_by`. 글 · 대상 · 번호는 처음 그대로다(트리거 `learned_rules_fixed`), 지우지 않는다. 횟수는 `rule_marks`를 넣은 만큼 version 없이 더한다. 색인: 공간 · 상태 · 대상(`learned_rules_active_idx`, 일을 빌려 줄 때 맞는 규칙)
- `rule_marks` (2026-11-28, 추가만 · 트리거 `platform.forbid_update_delete`): 규칙 하나를 센 근거. `source`(`verdict:<판정 작업>` · `approval:<결재>`) · `mark`(helpful · harmful) · 따른 작업 `task_id`. `UNIQUE(rule_id, source)`라 같은 판정 · 수정 요청이 두 번 와도 한 번이다
- `agents.scopes`에는 `run`을 넣을 수 없다 (CHECK). 러너만 일을 빌린다. `browse`(서버 브라우저로 하는 작업)는 `read_all` · `write`와 함께 둘 수 없다 (CHECK `agents_browse_not_private`. `write`도 임시 글 · 소재를 연다). `code`(코드 러너 칸에서 하는 코드 작업)도 `read_all` · `write`와 함께 둘 수 없다 (CHECK `agents_code_not_private`). `make`(코드 러너 칸에서 파일을 만드는 작업)도 같다 (CHECK `agents_make_not_private`). 만들기 작업의 재료(주인이 고른 결과물 · 위키 id)는 표의 칸이 아니라 `tasks.payload.make`에 둔다. `approval_actions`는 결재를 올려 할 수 있는 동작이다. 쉬는 중인지는 저장하지 않고 계산한다.
- `tasks`: `target_*`는 다른 모듈의 대상이고 값으로만 둔다. `(space_id, request_id)`가 유일해서 같은 일 요청은 한 번만 들어온다.
- 위임 (`tasks.parent_id` · `depth` 0~3 · `rounds` 0~3 · `wait_reason`): 새 상태 없이 `waiting`에 무엇을 기다리는지(`approval`·`subtasks`)만 적고, `(status = 'waiting') = (wait_reason IS NOT NULL)`을 DB가 지킨다. 하위 작업의 `request_id`는 `delegate:<위 작업>:<AI의 id>`. 위 작업을 취소하면 아래 작업도 위 → 아래 순서로 잠가 함께 취소한다. 하위 작업을 기다리는 동안의 기한은 `wait_until`(팀원 기다리기 2026-11-19, `wait_reason = 'subtasks'`일 때만 있다: DB CHECK `tasks_wait_until_subtasks`, 부분 색인 `tasks_wait_until_idx`)이고, 지나면 마감 작업이 위 작업을 깨운다. 깬 까닭은 `payload.wake`(all · failed · deadline · owner). 대화의 일(회차 · 덧붙인 말의 답 · 검토)은 `priority` 10으로 만들어 배경 일(0)보다 먼저 빌려 주고, 하위 작업은 위 작업의 우선순위를 물려받는다.
- `task_events`: 실행 기록. 보드, 오피스, 사용량이 같은 로그를 읽는다.
- `approvals`: 작업 하나에 기다리는 결재는 하나다 (부분 유일 인덱스). 한도 올리기처럼 작업이 없는 결재는 `task_id`가 비어 있다. 결과 결재 (2차 2단계): 대화의 일에서 올라온 결재는 `chat_id`(사람에게 따로 알리지 않음, 바로 알릴 동작은 비운다)를 갖고 결과 카드에 실리면 `card_id`가 그 카드를 가리킨다. 카드도 이 표의 한 줄(동작 `task.chat.result`, 대상 `chat` · 대화 id, 판은 회차)이고 대화마다 기다리는 카드는 하나다 (부분 유일 인덱스 `approvals_one_card`). 결재 화면은 `target_*`로 대상 모듈의 API에서 실제 내용을 읽고, AI가 쓴 요약을 보여 주지 않는다. 검수(2026-11-20): `inspected_at`은 검수가 끝난 때(통과 · 고칠 것 · 넘김), `agent_decided`는 검수자가 정했는가(통과면 승인 · 고칠 것이면 수정 요청, `decided_by`는 검수자 에이전트). 넘긴 결재는 기다린 채 메모에 검수 의견이 붙어 결과 카드에 실린다. 기한(L3, 2026-11-28): `expires_at`이 지나면 서버가 정한 대로 한다 (지금은 확인 필요 판단 `task.decision`만: 추천안으로 승인, `agent_decided`). 기다리는 결재의 기한은 부분 인덱스 `approvals_expiring_idx`로 찾는다 (`DecisionLapseJob`). 판단 승인의 `payload`는 판단 한 줄 · 고른 안 · 다른 안 · 까닭 · 확인 필요의 까닭 · 대화와 정해진 안(`picked`).
- `plan_usage`: 러너가 본 마지막 값 하나만 둔다. `window`가 예약어라 열 이름은 `period`다. `percent`는 초과 사용이면 100을 넘고, `resets_at`이 지나면 확인 전으로 본다.
- `ai_logins`: 공간과 도구(`claude`·`codex`)마다 한 줄. 자격은 서버 키로 암호화한다. Claude 토큰의 `expires_at`은 저장한 날부터 1년이고(CLI가 남은 기간을 알려 주지 않는다), Codex의 `auth.json`은 갱신 토큰이라 비운다.
- `schedules`: 정해진 시각에 작업을 만든다 (7단계에서 `heartbeats`를 넓혀 옮겼다). 이름 · 담당(`agent_id`, 비면 자동 배정이고 지시가 있어야 한다) · 지시 · 목표. 주기는 `daily`(시간대 기준 하루 중 분 + ISO 요일)나 `hourly`(N시간마다)나 `minutely`(`every_minutes` 5~720분, 시간대 기준 자정부터 N분 간격, 2026-11-20)나 `once`(`run_at` 한 번, 돈 뒤 꺼진다, 2026-11-27 캘린더, CHECK `(mode = 'once') = (run_at IS NOT NULL)`), 시간대는 IANA 이름. 켜져 있으면 늘 다음 시각이 있다 (CHECK). 하루 한도 `daily_max`(1~288, 저절로 만든 작업만 센다. "지금 실행"은 세지 않는다)는 `run_day`(시간대 기준 "YYYY-MM-DD", 글자라 Date로 바뀌지 않는다)와 그날 만든 수 `day_runs`로 센다. 만든 작업의 `request_id`는 `schedule:<스케줄>:<시각>`이라 일꾼이 두 번 돌아도 작업은 하나다.
  2차 5단계에 자동화 레시피가 되었다 (새 표 없이): `destination`(task · chat · page, page면 `page_id`가 있다 · CHECK), `page_id`(blog의 값, 외래키 없음), `deliver`(받을 것, chat일 때만 · CHECK, 대화와 같은 목록), `rules`(지킬 것, 2000자), `trigger`(time · manual · after), `after_id`(앞 레시피, 같은 표의 외래키 `ON DELETE SET NULL`, 자기 자신은 안 됨), `chat_id`(회차를 쌓는 대화, `ON DELETE SET NULL`. 대화에서 승인한 대화 레시피는 승인할 때 그 대화로 정해진다, O-3. 받을 것은 대화가 아니라 회차마다 싣고(`payload.chat.deliver`), 받을 것을 바꿔도 대화는 그대로이며 대화가 아닌 곳으로 보내게 바뀔 때만 비운다, O-4). 다음 시각은 켜져 있고 계기가 time일 때만 있다 (CHECK `schedules_next_check`). `mail`(2026-11-27, 기본 false, chat일 때만 · CHECK `schedules_mail_chat`): 회차의 최종 답 · 실패를 관리자 메일로도 보낸다. 회차 작업의 `payload.chat.mail`로 싣고(서버가 다시 맡긴 회차도 물려받는다) `task.chat.said`의 `mail`이 되어 메일 플러그인이 받는다. 받는 사람은 메일 플러그인의 받을 주소(관리자) 하나다.
- `skills` + `skill_revisions`: 러너 스킬(`moida-where: runner`)의 콘솔 판. 스킬 하나에 한 줄(`(space_id, name)` 유일)이 쓰는 판(`active_revision`, 비어 있으면 저장소 판)과 판 수를 든다. 판은 추가만 하고(`files`는 `SKILL.md`와 `references/*.md`의 경로 → 글, `hash`는 경로 순으로 이은 sha256, `based_on`은 고치기 시작한 판의 해시), 되돌리기는 `active_revision`만 옮긴다. 아직 줄이 없는 스킬의 첫 저장은 advisory 잠금(`task.skill:<공간>:<이름>`)으로 하나만 만든다. 저장소 판은 표에 없고 서버가 `skills/`에서 읽는다

- `api_connectors` (2026-11-24 도구를 찾아 붙이기, MCP 9장): 일꾼이 낸 정의서로 붙인 REST API 하나. `name`(공간에 하나, api_run의 connector), `base`(https 출처 + 앞 경로, 테스트의 루프백 http만 예외 CHECK), `spec`(거른 정의서, 64KB까지 CHECK), `pending_spec`(승인을 기다리는 새 버전), `history`(앞 정의서 10개), `secret` · `nonce`(머리글마다 키를 JSON으로 묶어 서버 키로 잠근 것, 짝 CHECK), `status`(proposed · active · off), `daily_max`(spend 동작의 24시간 한도 0~1000, 기본 20), `source`(어디서 찾았는지), `proposed_by`(→ `agents`, 지우면 NULL), `last_used_at` · `last_error`(버전 없이 적는다). 서버 키를 바꾸면 `pnpm secret:rotate`가 다시 잠근다.

## 6b. `community` (스토어 3-1)

커뮤니티의 회원 · 글 · 댓글 · 신고. 관리자 계정(`account`)과 표 · 쿠키 · 권한을 나눈다 (원칙 10). 설계는 [스토어](스토어.md) 11.5.

- 모듈 사이 외래키는 없다: 앱은 blog의 것이라 `app_id`는 값이다. 모듈 안(`account_sessions.account_id`, `members.account_id`)은 외래키를 둔다.
- `members`: 회원은 앱마다 따로다. 닉네임은 앱 안에서 하나(`members_nickname_key`: `(app_id, nickname_key)`, 열쇠는 소문자 · 공백 · 구두점 없이 `Nickname.keyOf`). `age_confirmed_at`은 가입할 때 만 14세 이상이라고 확인한 때. `blocked_until`이 지나지 않았으면 쓰기 · 신고 · 닉네임 바꾸기를 막는다 (무기한은 9999-12-31: DB의 infinity는 Date로 읽히지 않는다). 아이디(`login_id`)는 앱 안에서 하나(`members_login_key`), 영문 소문자로 시작하는 4~20자(CHECK)이고 바꾸지 않는다. 비밀번호는 scrypt 해시(`password_hash`, CHECK `scrypt$…`)와 바꾼 때(`password_changed_at`)만. 이메일 · IP는 없다. 가입할 때 동의한 약관 버전(`terms_version` · `privacy_version`, 3-4 전에 가입한 회원은 NULL). 탈퇴(3-4, `community_terms_leave`)하면 `left_at`을 남기고 개인정보를 지운다: `login_id`는 `left:<id>`, `password_hash`는 빈 값, 닉네임 "탈퇴한 회원" · `nickname_key` `left:<id>`, 차단 메모 · 마지막 접근은 NULL (CHECK는 탈퇴한 회원에만 이 값을 허용한다). 같은 아이디 · 닉네임을 다시 쓸 수 있다.
- `accounts` (2026-11-26, 스토어 계정): 공간(스토어)에 계정 하나. 메일 · 아이디는 공간에서 하나(부분 유일 색인 `accounts_email_key` · `accounts_login_key`), 옮겨 온 옛 계정은 둘 중 하나가 비어 있을 수 있다. 공통 약관에 동의한 버전 · 정지(`suspended_until`) · 탈퇴(`left_at`: 메일 · 아이디 null, 해시 '', CHECK `accounts_state_check`). `members.account_id`는 그 계정의 앱 참여(같은 계정은 앱마다 하나: `members_account_key`, 나가면 null, CHECK `members_account_check`). 메일 · 아이디 · 비밀번호 해시는 `members`에서 계정으로 옮겼다(`community_accounts`, 메일마다 계정 하나로 합치고 아이디 회원은 회원마다 하나). `news_agreed_at`(2026-11-27): 가입 화면 · 내 정보의 "(선택) 소식 메일 받기"에 동의한 때, 탈퇴하면 null(CHECK `accounts_news_left`). 받는 사람 목록은 메일 플러그인의 `email.subscribers` 계정 줄(`account_id` · `space_id`, 앱 없음)이 갖고, 보낼 소식은 `email.sends`의 `kind: news`(제목 · 본문 · `request_id`, draft → 결재 `email.news.send` 승인 → sending).
- `account_sessions` (전 `member_sessions`): 앱 도메인의 `moida_member` 쿠키. 계정과 그 앱(`app_id`)을 가리켜 앱에 참여하기 전에도 열린다. 해시만 두고 마지막 사용부터 30일(`expires_at`을 늘린다), 로그아웃 · 비밀번호를 바꿔 끝난 다른 로그인 · 정지 · 탈퇴는 `ended_at`.
- `terms`의 `space_id`(2026-11-26): 공간의 공통 약관(`app_id` null, `terms_owner_check`로 둘 중 하나만, `terms_store_version_key`).
- `topics` + `topic_revisions`(추가만, 트리거): 글과 그 버전. `revisions`는 버전 수, 제목 · 본문이 바뀔 때마다 하나 쌓인다. `state`는 `shown` · `hidden` · `removed` · `deleted`(어느 상태든 내용 · 버전은 남는다), `body_key`는 같은 본문을 되풀이하는지 보는 열쇠(공백을 정리한 본문의 sha256). `(member_id, request_id)` 하나라 같은 요청은 글 하나. 목록은 `(app_id, state, id DESC)`, 쓰기 한도는 `(member_id, created_at DESC)` 색인으로 센다
- `comments`: 댓글 (고치지 않는다, 답글 없음). 상태 · `body_key` · `request_id`는 글과 같다. 글 아래 목록은 `(topic_id, id)`
- 가림 (3-1c, `community_moderation`): 글 · 댓글의 `hidden_by`는 가린 까닭(`reports`: 신고가 쌓여 시스템이, `owner`: 관리자가), 가려진(`hidden`) 것에만 있다 (CHECK `topics_hidden_by` · `comments_hidden_by`). `decided_at`은 관리자가 마지막으로 정한 때이고 그보다 앞선 신고는 임시 가림에 세지 않는다
- `reports`: 신고 (글 · 댓글 가운데 하나 CHECK `reports_target`). 한 회원이 같은 대상에 한 번(부분 유일 색인 `reports_once_topic` · `reports_once_comment` → 409). `state`는 `open` → `accepted`(가림 · 내림) · `dismissed`(되돌림), 닫히면 `closed_at`(CHECK `reports_closed`). 관리 목록은 `reports_open (app_id, id DESC) WHERE state = 'open'`, 시간당 한도는 `reports_member (member_id, created_at DESC)`. 신고한 회원은 관리자에게만 닉네임으로 보인다
- `decisions`(추가만, 트리거): 관리 결정 기록. 대상은 글 · 댓글 · 회원 가운데 하나(CHECK `num_nonnulls = 1`), `action`은 `hide` · `show` · `remove` · `block` · `unblock` · `reset_password`, `by_kind`는 `system`(신고로 임시 가림) · `owner`(관리자, `by_id`), 메모 500자. 3-3에서 승인한 AI 운영 팀의 의견이면 값을 더한다. 목록은 `decisions_app (app_id, id DESC)`
- `terms`(추가만, 트리거, 3-4): 앱마다 약관 버전. `kind`는 `terms`(이용약관) · `privacy`(개인정보처리방침), `version`은 1부터, `(app_id, kind, version)` 유일(`terms_version_key`: 그사이 다른 버전이 올라오면 409). 본문은 마크다운 1~50,000자. `by_kind`는 `owner`(관리자가 바로) · `approved`(일꾼의 제안을 승인), `by_id`는 그 관리자. 공개된 것은 마지막 버전
- `app_tables` (앱 플랫폼, [스토어](스토어.md) 12.4): 앱이 선언해 열린 표의 목록. `(app_id, name)` 유일, `columns`(jsonb: 칸 → 타입) · `read_rule` · `write_rule` · `open`(선언에서 빠지면 false, 줄은 남는다) · `applied_seq`(맞춘 앱 코드 버전) · `space_id`. API는 이 목록의 이름만 SQL에 쓴다
- 앱마다 스키마 `app_<앱 id의 16진 32자>` (실행 중에 생긴다, 마이그레이션 · 표 인터페이스에 없다): 선언한 표마다 실제 표. 모든 표에 `id uuid`(UUIDv7) · `owner uuid`(넣은 회원, 관리자 · 일꾼이 넣은 줄은 NULL) · `created_at` · `updated_at`, 선언한 칸은 NULL 허용(`text` · `bigint` · `double precision` · `boolean` · `timestamptz` · `jsonb`). 표마다 행 수준 보안을 켜고 정책 `moida_read` · `moida_insert` · `moida_update` · `moida_delete`를 역할 `moida_app`(로그인 없음, 마이그레이션이 만든다)에 건다. 회원 쪽 쿼리는 트랜잭션에서 `SET LOCAL ROLE moida_app`과 `moida.member`를 정한 뒤 돈다. 지우는 DDL은 없다 (원칙 2)

## 7. 트랜잭션과 동시성

기준: **데이터를 잃지 않는 곳까지는 막지 않고, 사람의 의도끼리 부딪히는 곳에서는 멈추고 사람에게 묻는다.**

1. 세션 올리기는 항상 새 판을 추가한다. 동시에 들어와도 서로 덮지 않는다.
2. 같은 요청은 `request_id`로 한 번만 반영한다.
3. AI가 생각하는 동안 트랜잭션을 열어 두지 않는다. 일을 빌리고, 밖에서 처리하고, 짧은 트랜잭션으로 제출한다.
4. 제출할 때 다시 검사한다. 본 뒤에 대상이 바뀌었거나 사람이 손댄 것이면 적용하지 않고 검토로 보낸다.

| 동작 | 순서 (한 트랜잭션) |
|---|---|
| 세션 올리기 | (트랜잭션 전에 민감정보 제거) → `idempotency` 자리 잡기 → 대화 자리 잠금(`pg_advisory_xact_lock`, 세션이 없어도) → 세션 `FOR UPDATE` → 없으면 만들기 → 내용 해시가 이미 있으면 판 없이 끝(`unchanged`) → 판 추가, `head_*` 갱신 → `outbox(vault.session.saved)` → 결과 기록 |
| 일 빌리기 | `task.tasks`에서 `queued` + 맡을 수 있는 에이전트 `FOR UPDATE SKIP LOCKED` → `running` + 작업 점유 시간(lease) 2분 (2026-11-17, `report_progress`가 늘린다) |
| 정리 결과 제출 | 묶음 자리 확인(`job_id`나 `idempotency`) → `change_sets` → 대상 잠금 → 변경마다 판정 → 바로 합칠 것은 적용 + `changes`, 검토는 `waiting`, 거부는 이유와 함께. 작업은 끝내지 않는다 (러너의 `submit_result`) |
| 콘솔 편집 | 묶음(`human`) → 대상 잠금 → `version` 비교 → 적용(사람 표시) → `changes` |
| 검토 승인 | 묶음 잠금 → 대상 잠금 → `base_version`이 다르면 `superseded` → 적용 + `changes` → 남은 검토가 없으면 묶음 `done` |
| 되돌리기 | 새 묶음(`revert`) → `changes`의 `before`로 적용 (대상이 그 묶음이 남긴 version과 다르면 409) → 원래 묶음 `reverted_by` |
| AI 초안 저장 | `idempotency` → 새 글이거나, 글 잠금 + `base_version` 비교 → 판 추가, wiki 연결 → 저장 |
| 공개 | 주인의 공개 범위 바꾸기, 또는 결재 뒤 `Post.publishApproved`. `status`·`published_at` → `outbox(blog.post.published)` |
| 복원 | 파일을 트랜잭션 밖에서 먼저 쓴다 → 잠금 → 빈 곳 확인 → 모듈마다 자기 스키마에 쓴다. 모듈을 한 트랜잭션에 묶는 유일한 곳이다 |

대상은 `종류:id` 글자 순서로 잠근다. 작업은 작업 → 결재 → 에이전트 순서로 잠근다.

부딪힐 때: 같은 대화를 두 번 올리면 하나씩 처리해 판을 둘 다 저장한다. 정리 결과와 사람 수정이 겹치면 늦은 쪽이 검토로 간다. 콘솔 두 곳에서 같은 글이나 wiki를 고치면 나중 저장을 409로 거절한다.

**세션 편집을 만들 때** (표 · 칸은 그때 만든다): 편집을 시작하면 잠금 대신 편집 임대 표에 행을 넣고 하트비트로 유지한다 (2분 끊기면 풀림). 그동안 그 세션의 정리 일과 AI의 연결 변경은 미룬다. 같은 세션의 새 원본은 막지 않고 저장하되 지금 판으로 올리지 않고 보류한 판으로 둔다. 편집 화면에는 새 원본이 들어왔다고 알리고, 아직 들어오는 중인 세션은 끝난 뒤 고치라고 권한다. 저장하면 시작한 판을 기준으로 칸 단위 3-way 합치기를 하고, 겹치면 편집 화면에서 고른다.

지원하지 않는 것: 세션 사이의 전역 순서 보장. 같은 세션 안의 판 순서만 서버가 받은 순서로 보장한다.

## 8. 인덱스

- 모든 외래키 열에 인덱스를 둔다. Postgres는 자동으로 만들지 않고, 없으면 삭제와 조인이 느려진다.
- 조회는 대부분 휴지통 제외라서 `WHERE deleted_at IS NULL` 부분 인덱스를 쓴다.
- 쓰기가 많은 판·로그 표는 인덱스를 최소로 둔다. 로그의 시각은 BRIN이다.
- 목록 화면은 필요한 열을 `INCLUDE`로 덮어 표를 읽지 않게 한다.
- 왜 있는지는 마이그레이션의 주석이 원본이다. 이름만으로 알기 어려운 것만 적는다.

| 인덱스 | 이유 |
|---|---|
| `tasks (space_id, priority DESC, id) WHERE status = 'queued'` | 일 빌리기. `SKIP LOCKED`와 함께 쓴다 |
| `task_events (at) WHERE tokens > 0` | 5시간·이번 달 사용량. 일을 빌릴 때마다 읽어서 토큰이 있는 기록만 훑는다 |
| `task_events (task_id) INCLUDE (tokens, at) WHERE tokens > 0` | 작업 몇 개의 토큰 합계 (대화 · 대화 목록 · 성적표 · 스킬 성적). 쿼리는 `tokens > 0`을 함께 건다 (2026-11-24 속도) |
| `tasks (space_id, request_id text_pattern_ops)` | request_id 앞부분 찾기 (`chat:<대화>:` · `lessons:<공간>:`). DB 정렬 규칙과 상관없이 LIKE 'x%'와 범위 `~>=~` · `~<~`가 탄다 (2026-11-24 속도) |
| `tasks (goal_id, id DESC) WHERE goal_id IS NOT NULL` | 목표별 작업과 목표의 작업 수 |
| `tasks (parent_id, id) WHERE parent_id IS NOT NULL` | 하위 작업과 남은 하위 작업 세기 |
| `schedules (next_run_at) WHERE enabled` | 일꾼이 때가 된 스케줄을 찾고(`SKIP LOCKED`), 가장 이른 다음 시각을 잰다 |
| `menus (space_id, sort, created_at)` | 공개 블로그의 메뉴 줄 순서 |
| `pages (menu_id) WHERE menu_id IS NOT NULL`, `posts (menu_id)`(옛 `posts_category_idx`), `posts (issue_id, issue_order)`(옛 `posts_series_idx`) | 메뉴 · 호의 글과 페이지 |
| `schedules (after_id) WHERE after_id IS NOT NULL` | 레시피의 일이 끝나면 그 뒤에 도는 레시피를 찾는다 (계기 after) |
| `tasks UNIQUE (space_id, payload->'page'->>'pageId') WHERE 대기 · 실행 · 기다림` | 한 페이지를 고치는 일은 한 번에 하나 (넘치면 409) |
| `tasks UNIQUE (space_id, payload->'appCode'->>'appId') WHERE 대기 · 실행 · 기다림` (`tasks_one_open_app_code`) | 한 앱의 코드를 고치는 일은 한 번에 하나 (스토어 1-6, 넘치면 409) |
| `notifications (space_id, created_at) WHERE push_sent_at IS NULL AND severity <> 'log'` | 푸시 일꾼이 깨어날 때(알림이 남거나 남은 알림의 때) 아직 다루지 않은 알림을 찾는다 (`SKIP LOCKED`) |
| `notifications (space_id, group_key) WHERE read_at IS NULL` | 같은 묶음 키의 안 읽은 알림을 바꾸거나 읽음으로 (`Notices.post` · `settle`) |
| `runners UNIQUE (device_id)` | 러너가 닿을 때마다 한 줄을 고친다 |
| `sessions (space_id, last_revision_at DESC) WHERE wiki_id IS NULL` | 도착 구역. 정리 전 세션만 담긴 작은 인덱스 |
| `change_sets (actor_id, created_at)` | "이 기기가 이때부터 한 일" 되돌리기 |
| `change_sets UNIQUE (space_id) WHERE kind = 'reorg' AND status IN ('open','review')` | 대정리는 한 번에 하나 |
| `change_ops (target_id) WHERE status = 'waiting'` | 대상이 바뀌면 기다리던 검토를 찾는다 |
| `session_revisions UNIQUE (session_id, content_hash)` | 같은 내용 재전송 감지 |

## 9. 보관과 정리

정해 둔 기간이다. **지금 지우는 일꾼은 결과물 휴지통(`OutputPurgeJob`)과 안 쓰는 파일(`BlobSweepJob`)뿐이고, 나머지는 아직 지워지지 않는다.**

| 대상 | 기간 |
|---|---|
| 휴지통 | 30일 (`purge_after`) |
| `platform.idempotency` | 30일 |
| `vault.changes` | 1년. 지나면 그 변경은 되돌릴 수 없다 |
| `vault.change_sets`, `change_ops` | 계속 (누가·왜·무엇을) |
| `task.tasks`, `task_events` | 계속 (실행 기록은 추가만, 한 달 사용량의 원본) |
| `task.skill_revisions`, `agent_revisions`, `task_runs` | 계속 (결과가 바뀐 까닭을 비교하는 원본) |
| `vault.run_memos` | 작업 세션과 함께 (세션을 영구 삭제하면 같이 지운다) |
| `mcp.tool_text_revisions` | 계속 (AI가 읽은 도구 글의 판) |
| `task.outputs` | 주인이 지울 때까지. 휴지통 30일 뒤 줄을 지우고, 파일은 아무도 쓰지 않으면 7일 뒤 |
| `task.output_shares` | 결과물과 함께 (바로 지우면 함께 지운다). 끈 · 기간이 지난 줄도 남긴다 (몇 줄 안 된다) |
| `blog.pages`, `page_revisions` | 계속 (지우는 길은 아직 없다. 결과물을 지워도 판이 가리키는 파일은 남는다) |
| `blog.app_code_versions` | 계속 (추가만. 앱을 지워도 남고, 버전이 가리키는 파일도 남는다) |
| `platform.notifications` 읽은 것 | 90일 |
| `platform.blobs` | 어느 도메인에서도 쓰지 않고 7일 |
