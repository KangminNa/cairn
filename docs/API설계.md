## 1. 세 입구

| 입구 | 쓰는 쪽 | 인증 | 용도 |
|---|---|---|---|
| REST `/api/*` | 콘솔, 블로그 | 로그인 쿠키 | 화면 데이터와 쓰기 |
| MCP `/mcp` | AI 도구, 러너 | OAuth, 기기 토큰, 작업 토큰 | 세션 저장, 작업 처리 |
| SSE `/api/stream` | 콘솔 | 로그인 쿠키 | 변경 알림 |

웹은 DB에 닿지 않고 REST만 부른다. REST와 MCP는 같은 Service·Query를 부르며, 진입 계층에 판단을 두지 않는다.

**AI의 입구는 `/mcp` 하나다.** Bearer 토큰(기기·작업)은 `/mcp`에서만 요청자가 되고, REST에서는 방문자와 같다 (`ActorGuard`). 방문자가 GET으로 닿는 경로와 응답 코드는 `apps/server/src/modules/platform/http/visitor-surface.api.test.ts`의 표가 원본이다: 새 경로나 열림·막힘이 바뀌면 그 표를 고쳐야 테스트가 통과한다. `/api/health`는 방문자에게 `status`만 주고, 확장·마이그레이션·표 수는 주인과 서버 자신에게만 준다.

## 2. 공통 규칙

| 항목 | 규칙 |
|---|---|
| 주소 | 명사 복수형. 상태를 바꾸는 동작은 `POST /:id/<동사>` |
| 버전 | REST는 웹과 함께 배포하므로 주소에 버전을 두지 않는다. MCP는 필드 추가만 하고, 깨지는 변경은 새 도구 이름으로 만들며 스킬을 함께 고친다 |
| 생성 | `requestId`로 중복을 막는다 |
| 수정 | `version`으로 낙관적 잠금. 어긋나면 409 |
| 목록 | 커서 방식 `{ <항목들>, next }`. 페이지 번호는 쓰지 않는다 |
| 오류 | `{ code, message, fields?, scope? }`. 코드는 [객체설계.md](객체설계.md) 3장. DB가 잠시 밀리면(잠금 5초 · 쿼리 30초) 503 `busy`: 같은 요청을 다시 하면 된다 (러너는 다시 보낸다). 알 수 없는 오류(서버 버그)는 500 `{ code: 'internal', message: '서버 오류예요 (요청 번호 …)', requestId }`: 오류 글은 싣지 않고 서버 로그에 요청 번호와 함께 남는다 |
| 요청 번호 | 모든 응답에 `X-Request-Id`(서버가 짓는 UUIDv7, 들어온 값은 믿지 않는다). 서버 로그의 요청 한 줄 · 오류 스택과 같은 번호다. 러너는 서버 쪽 실패 문구에 붙인다 (리팩토링 6단계). 그 요청이 남긴 이벤트(outbox `trace_id`)와 일꾼의 처리 로그 · 거기서 이어 남긴 이벤트도 같은 번호다 (리팩토링 R1) |
| 형식 | JSON camelCase, ID는 UUIDv7, 시간은 ISO 8601 |
| 공개 범위 | Query가 Actor를 받아 서버에서 거른 뒤 순위와 개수를 계산한다 |
| 타입 | 표 인터페이스의 타입만 가져오는 `<이름>.view.ts`의 `toJSON()`이 실제 모양을 돌려주고, 웹은 이 파일만 `import type`으로 가져온다. `pnpm check`가 어긋남을 잡는다. 웹의 `_lib/types.ts`에는 오류 모양(`ApiError`)만 둔다 |

## 3. REST 경로

경로의 원본은 코드다. 아래는 3단계부터 만든 경로다.

| 메뉴 | 경로 | 단계 |
|---|---|---|
| 계정 · 사이트 | `GET /api/auth/me` → `{ login, displayName, name, version }` (`name`은 화면에 보일 이름: `displayName`, 없으면 아이디. 주인만), `PUT /api/auth/me/profile { displayName, version }` → 같은 모양 (비우면 아이디로, 40자까지, 낡은 version 409). `GET /api/space` → `{ name, description, siteUrl, installed, version, hostedApps, logoUrl }` (누구나. `logoUrl`은 `/api/space/logo?v=<해시 앞 12자>` 또는 null), `PUT /api/space/logo?version=` (본문은 그림 파일 그대로, 머리글 `image/*`. PNG · JPEG · WebP · GIF만 415, 1MB 413, 낡은 version 409. 주인만) → 공간, `POST /api/space/logo/delete { version }` → 공간, `GET /api/space/logo` (누구나, `nosniff` · `Content-Security-Policy: sandbox`, 없으면 404) | 2026-11-14 |
| 보안 | `GET /api/auth/sessions` → `{ sessions: [{ id, current, createdAt, expiresAt, lastSeenAt, ip, lastIp, userAgent }], limits: { sessionDays, triesPerLogin, triesPerPlace, windowSeconds } }` (끝나지 않은 로그인, 최근부터. 이 브라우저는 `current`. 로그인은 마지막으로 쓴 날부터 `sessionDays`(30)일이라 `expiresAt`은 쓸 때마다 늘어난다. 로그인 쿠키 `moida_session`은 400일이고 살아 있는지는 서버가 정한다, 웹 UX U2 2026-11-19), `POST /api/auth/sessions/:id/end` → `{ ended: true }` (다른 곳의 로그인 하나. 지금 로그인 422, 없는 로그인 404, 이미 끝났으면 그대로 200), `POST /api/auth/sessions/end-others` → `{ ended: true }` (지금 로그인만 남김), `GET /api/security/events?group=&cursor=` → `{ events: [{ id, kind, at, lastAt, count, ip, userAgent, detail }], next }` (보안 기록 50개씩 최근부터, `group`은 종류의 앞 마디: login · session · password · install · device · runner · access. `detail`은 method · login · path · status · code · credential · device · reason 중 있는 것). 모두 주인만. `GET /api/devices`의 기기에 `lastSeenAt` · `lastIp` | 2026-11-15 |
| 처리 실패 | `GET /api/events/failed` → `{ items: [{ id, topic, data, attempts, lastError, traceId, createdAt, failedAt }] }` (8번 실패해 멈춘 이벤트, 최근에 멈춘 것부터 50개. `data`는 이벤트가 실은 값에서 판 번호 `v`를 뺀 것), `POST /api/events/:id/retry` → 그 이벤트 하나(`failedAt` null): 처음처럼 다시 시도하게 돌리고 일꾼을 깨운다. 공간에 멈춘 것이 더 없으면 "처리 실패" 알림이 읽음이 된다. 없는 번호 · 다른 공간 404, 멈춘 것이 아니면 409, 번호 모양이 틀리면 400. 모두 관리자만. 명령줄 `pnpm run events failed` · `retry <번호|--all>`은 모든 공간 | 리팩토링 R1 |
| 작업 | `GET /api/tasks?status=&goalId=&cursor=`, `POST /api/tasks { requestId, instruction, agentId?, goalId?, kind?, materials?, page? }` (`page: { title?, pageId? }`는 만들기 작업에만: 끝나면 결과물 묶음이 페이지의 새 판이 된다. `pageId`가 없으면 새 페이지. 작업 응답의 `page`는 `{ pageId }` 또는 null. `appCode: { appId }`(스토어 1-6)도 만들기 작업에만: 끝나면 결과물 묶음이 그 앱 코드의 새 버전이 된다(앞 버전 · 시작 코드 위에 얹는다, `page`와 함께 적지 않는다, 한 앱에 한 번에 하나 409). 작업 응답의 `appCode`는 `{ appId }` 또는 null. 만들기 작업은 `kind: 'make'`, `materials: { outputIds[], wikiIds[] }` 각각 10개까지 → `payload.make`. 없거나 휴지통의 결과물, 만들기가 아닌 일의 재료는 422), `GET /api/tasks/:id` (+ `goalChain`: 회사 목표부터 이 작업의 목표까지, `runs: [{ seq, startedAt, agentRevision, skill: { name, source, revision, hash } \| null, runnerBuild, cliVersion, model }]`: 빌려 줄 때마다 어떤 규칙으로 돌았는지, 처음부터, `outputs: [{ id, name, kind, mime, sizeBytes, runSeq, createdAt }]`: 이 작업이 만든 결과물, 휴지통 것은 빼고), `POST /api/tasks/:id/cancel { version }`, `POST /api/tasks/:id/wake` (판단 바꾸기, L1 2026-11-21: 하위 작업을 기다리는 작업을 바로 깨운다(`wake: change`). 재촉과 달리 그 뒤에도 다시 맡기기 · 기다리기를 막지 않는다. 기다리는 중이 아니면 409. 관리자만. 화면은 판단의 "바꾸기"를 덧붙인 말로 보낸 뒤 회차가 팀원을 기다리는 중이면 부른다), `POST /api/tasks/:id/hurry` (지금까지로 답하기, 팀원 기다리기 2026-11-19: 하위 작업을 기다리는 작업이면 바로 깨우고(`wake: owner`), 대기 · 실행 중이면 그 뒤로 더 맡기거나 기다리지 못하게 적어 둔다. 승인을 기다리거나 끝난 작업은 409. 관리자만) | 3 |
| 결재 | `GET /api/approvals`, `GET /api/approvals/:id`, `POST /api/approvals/:id/decide { version, decision: approve·revise·reject, note?, picked?, choice? }` (확인 필요 판단(L3, 2026-11-28, 동작 `task.decision`): 결재의 `decision: { text, chosen, alternatives, why, confirm, chatId, picked? }` · `expiresAt`. 승인의 `choice`는 고른 안(0 추천안 · 1~ 다른 안, 비우면 추천안, 없는 안이면 422)이고 작업은 그 안을 `payload.decided: { text, chosen, picked, note, lapsed }`로 받아 대기열로 돌아간다. 수정 요청은 `picked` 없이 메모가, 반려는 작업을 멈춘다. 기한이 지나면 일꾼(`DecisionLapseJob`)이 추천안으로 승인한다(`agentDecided`, `lapsed: true`). 알림 제목은 "판단을 골라 주세요", 링크는 그 대화) (2차 2단계: 목록은 대화의 일에서 올라온 결재(`chatId`)를 빼고 결과 카드(`action` `task.chat.result`, 대상 `chat`)를 보인다. 그런 결재를 하나씩 정하면 422 "결과 카드에서 정해요". 카드의 `picked`는 고른 항목 id(실린 결재 · 결과물, 비우면 모두, 카드에 없는 id면 422): 승인 → 고른 결재는 승인 · 고르지 않은 결재는 반려 · 고르지 않은 결과물은 휴지통, 수정 요청 → 그 대화의 도는 일을 멈추고 메모를 다음 회차로, 반려 → 도는 일을 멈추고 결과물을 모두 휴지통으로. 항목이 더해지면 카드의 `version`이 올라 낡은 판은 409) 설정 바꾸기(2026-11-15 C): 결재 · 카드 항목의 `changes: [{ field, before, after, grant }]`(다른 결재는 null)는 승인하면 바뀔 칸이다. 승인 이벤트(`task.approval.*`)에 `payload`(서버가 적은 바뀔 값)가 실린다. 검수(2026-11-20): 결재의 `inspectedAt`(검수가 끝난 때, 아니면 null) · `agentDecided`(검수자가 통과 · 수정 요청으로 정했으면 true, `decidedBy`는 검수자 에이전트 id). 검수가 끝나면 이벤트 `task.approval.inspected`. | 3 |

결재는 작업에 묶이지 않는 경우(한도 변경 등)가 있어 작업 아래에 두지 않는다. 결재 메뉴는 위키 제안도 함께 보여 주되, 데이터는 각 모듈이 따로 가진다.

작업 목록의 `lastEvent`는 마지막 실행 기록의 앞 200자다. `POST /api/tasks`의 제목은 지시의 첫 줄, 종류는 `general`이 기본이다. 일 요청 이벤트는 `kind`, `title`, `target*`, `baseVersion`, `priority`까지 적는다.

작업 상태: `queued → running → waiting → running → done`, 실패는 `failed`, 취소는 `cancelled`. 결재 상태: `pending → approved · rejected · revision_requested · cancelled`.

MCP 입력과 응답은 snake_case다.

- `next_jobs { wait_seconds?, limit?, tools?, signin_tools?, own_logins?, browser?, connector_check?, runner_build?, cli_versions? }`는 최대 25초 기다리는 긴 폴링이다. 러너는 할 수 있는 것을 알린다: `tools`는 일할 수 있는 AI CLI, `signin_tools`는 웹 로그인을 대신 돌릴 수 있는 CLI, `own_logins`는 러너가 스스로 가진 로그인(환경 변수 등), `browser`는 서버 브라우저에 붙어 있는지(알리지 않으면 false), `connector_check`는 커넥터 연결 확인(`tool_check`)을 할 수 있는지(알리지 않으면 false: 확인 일을 모르는 옛 러너가 AI로 돌리지 않게, 2026-11-15). 서버는 그 도구의 로그인을 쓸 수 있을 때(또는 `own_logins`에 있을 때)만 에이전트의 일을, `tools`에 있고 서버의 로그인을 쓸 수 있을 때만 연결 확인을, `signin_tools`에 있을 때만 웹 로그인을, `browser`가 true일 때만 브라우저 작업(`browse`)을 빌려 준다. 코드 작업(`code`)은 코드 러너 칸 기기(기기 권한 `sandbox`)에게만 주고, 칸에는 코드 작업만 준다: 러너가 알리는 값이 아니라 기기로 정한다. 갱신 토큰이 바뀌는 도구(Codex)는 서버의 로그인으로 공간에서 한 번에 하나만 돈다. 알리지 않은 값은 거르지 않는다(알리기 전의 러너). 일이 생기면 바로 돌려준다. 응답은 `{ jobs: [{ task, instruction, deliver, target, skill, revision_note, agent, run_token, goal_chain, team, subtask_results, rounds_left, wake }] }`. `wake`는 하위 작업을 기다리다 깬 까닭(팀원 기다리기 2026-11-19: `all` 모두 끝남 · `failed` 하나가 실패 · `deadline` 기한이 지남 · `owner` 관리자가 지금까지로 답하라고 함 · `help` 팀원이 `ask_help`로 도움을 청함(2026-11-20), 처음 빌리는 일이면 null)이고, 먼저 깼으면 `subtask_results`에 끝나지 않은 하위 작업도 `status`(queued · running · waiting) · `waiting`(approval · subtasks) · `since`(맡긴 때) · `progress`(최근 진행 기록 3줄과 "도움 요청:" 줄 전부, 줄마다 300자, 오래된 것부터, 끝난 일은 빈 목록, 2026-11-20)와 함께 실린다 (`task_id`는 `wait_subtasks`의 `cancel`에 쓴다). `deliver`는 맡긴 팀장이 정한 결과 형식(위임한 하위 작업에만, 없으면 null, 2026-11-17 D1). `goal_chain: [{ title }]`은 회사 목표부터 이 작업의 목표까지, `team: [{ agent_id, name, role, status, kinds, bound, tool, open, recent: { done, failed, revised }, connectors, team: { members, kinds: { 종류: 수 }, connectors: { 이름: 수 } } | null }]`는 바로 아래 팀(없으면 빈 목록, `bound`는 정해진 러너에서만 일하는 팀원. 대표(O-2)의 일이면 맨 위 에이전트 전부, `team`은 그 아래 팀 전체(손자 팀까지)의 - `set_plan { steps?, criteria, must_not? }` → `{ fixed: true, steps, criteria, must_not }` (큰 일은 계획 먼저 2026-11-20, 작업 토큰): 맡은 일의 계획을 한 번 정한다 (단계 8 · 완료 조건 1~8 · 하지 말 것 5개까지, 한 줄 200자). 작업의 `payload.plan`에 고정되어 다시 부르면 `rule_violation`(진행 장부의 진전 없음이 3번 이어진 뒤에는 한 번 더 받는다: 단계 · 하지 말 것만 바뀌고 `criteria`는 비우거나 처음 것 그대로, 다르면 `rule_violation`, 2026-11-28), 끝난 일이면 `conflict`, 남의 일이면 `forbidden`. 대화의 일이면 소식(`decision`)으로도 남는다. 검토 · 검수 지시문이 대화의 회차(다시 맡긴 회차는 그 줄의 처음 회차)에서 가장 먼저 정한 계획의 완료 조건 · 하지 말 것을 그대로 받고, 러너는 깨어난 일에 다시 보인다 (`JobPlan`). `next_jobs`의 팀원(`team[]`)에는 `scorecard: { judged, first_pass, avg_fixes, decided, sent_back, tokens_per_done } | null`(최근 30일 성적표)이 실린다.
- `note_progress { done, progressing, looping, next, why? }` → `{ stalled, replan }` (진행 장부 2026-11-28, Magentic-One의 progress ledger, 작업 토큰, 대표만): 하위 작업 결과를 받고 깬 실행에서 다음 동작 전에 한 줄 판단을 남긴다. 진전 없음(`progressing: false` 또는 `looping: true`, 끝나지 않음)이 이어진 수를 작업의 `payload.ledger { stalled, replan, last }`에 두고, 3번(`ProgressLedger.STALL_LIMIT`)이면 `replan: true`: `set_plan`을 한 번 더 받고 러너가 깬 실행의 지시문에 틀 `ledger`를 싣는다. 대화의 일이면 소식 `progress`(`data.ledger`, 글은 상태 한 줄: "다음: …" · "진전이 없어 계획을 다시 세우는 중")로 남고, 이 소식은 `post_update`의 20개와 따로 센다(작업마다 20개). 대표가 아니면 `forbidden`, 끝난 일이면 `conflict`.
- `ask_help { part }` → `{ asked: true, lead_woken }` (팀원 돕기 2026-11-20, 작업 토큰): 팀장이 맡긴 일(위 작업이 있는 일)을 하는 팀원이 떼어 낼 부분(무엇을 · 어디까지 · 돌려줄 결과, 1,000자)을 적어 도움을 청한다. 실행 기록에 "도움 요청: …" 한 줄을 남기고, 팀장의 일이 하위 작업을 기다리는 중이면 먼저 깨운다(`wake: help`, `lead_woken: true`). 이미 깨 있으면 기록만 남긴다(`lead_woken: false`, 팀원이 그 부분도 직접 한다). 요청한 팀원의 일은 그대로 돈다. 일 하나에 2번(넘으면 `rule_violation`), 맨 위 일이면 `rule_violation`, 실행 중 · 살아 있는 임대가 아니면 `conflict`.
- `ask_lead { question }` → `{ asked: true, waiting: true, lead_woken }` (대표 ↔ 일꾼 대화 2026-11-24, 작업 토큰): 대표가 맡긴 일(위 작업이 있는 일)을 하는 일꾼이 대표에게 묻는다 (1,000자). 그 일은 대표의 답을 기다리고(`waiting`, `wait_reason: lead`) 이 실행은 끝난다. 대표의 일이 하위 작업을 기다리는 중이면 먼저 깨운다(`wake: question`). 깬 대표의 `subtask_results`에는 그 일이 `waiting: lead`로, 질문이 `summary` 자리에 실린다. 일 하나에 3번(넘으면 `rule_violation`), 맨 위 일이면 `rule_violation`.
- `reply_worker { replies: [{ task_id, text }] }` → `{ replied, waiting: true }` (대표만, 5개까지, 답 2,000자): 답을 기다리는 바로 아래 일에 답한다. 답은 그 일의 `payload.leadTalk.replies`(`{ q, a }` 오래된 것부터)에 쌓이고 그 일은 대기열로 돌아가 이어서 한다 (러너가 "# 대표의 답"으로 그린다, 같은 러너면 CLI 세션을 이어서). 대표의 일은 다시 하위 작업을 기다린다 (라운드를 쓰지 않는다). 바로 아래 일이 아니면 `not_found`, 답을 기다리지 않는 일이면 `conflict`, 관리자가 재촉한 일이면 `rule_violation`.
- `report_round { summary, done, completed?: string[], remaining?: string[], evidence?: [{ url? | output_id?, note? }], next_plan?, milestone? }`: 목표 실행의 회차 보고 (작업 토큰). 회차 작업(`request_id`가 `goal-run:<실행>:<회차>`)이 아니거나, 이미 보고했거나, 지금 도는 회차가 아니면 `rule_violation`. 답은 보고 한 줄(`{ round, taskId, summary, completed, remaining, evidence, nextPlan, done, milestone, createdAt }`). 근거의 `url`은 http · https만(화면이 링크로 그린다). 보고는 추가만 하고, 회차 작업이 끝나면 일꾼이 다음을 정한다: `done: true` → 최종 결재, 결재 시점(`every`는 늘, `milestone`은 `milestone: true`일 때) · 회차 한도 · 한 일이 없고 남은 일도 줄지 않음 · 보고 없이 끝남 · 실패 · 취소 → 중간 결재, 아니면 다음 회차. 다음 회차의 지시에는 앞 회차 보고와 결재에서 주인이 남긴 말이 실린다. `read_url`의 기준은 회차 작업의 지시가 아니라 실행의 지시다 (앞 회차 보고는 AI가 쓴 글)
- `blog_get_post { post_id }`는 `{ post_id, title, body_md, status, version, tags, main_wiki_id, ref_wiki_ids }`, `blog_save_draft { request_id, post_id?, base_version?, title, body_md, tags?, main_wiki_id?, ref_wiki_ids? }`는 `{ post_id, version, status, url }`를 돌려준다. 볼 수 없는 wiki는 응답에서 빠지고, 넣으면 없는 wiki처럼 404다. 값을 보내지 않으면 그대로, `main_wiki_id: null`과 `ref_wiki_ids: []`는 비우기다. 참고는 20개까지. AI는 임시 글만 쓰고 고친다. `post_id`가 있으면 `base_version`이 꼭 있어야 한다: 사람이 그사이 고친 내용을 AI가 모르고 덮지 않게. `request_id`는 작업 토큰이면 작업마다 따로 센다. 제목 · 본문의 비밀값은 판이 되기 전에 `[지움: 종류]`로 바뀐다. `basket_get {}`은 `{ items }`를 돌려준다.
- `submit_changes { request_id, message, ops: [{ op, target_id?, base_version?, payload }] }`는 vault 소유다. 변경 묶음을 쓰고 `{ change_set_id, ops: [{ seq, verdict, status, reason }] }`로 판정을 바로 돌려준다. `ops`의 대상은 변경마다 다르다: `wiki.create { title, body_md, slug? }`, `wiki.revise { target_id, base_version, title?, body_md }`, `session.assign { target_id, base_version, wiki_id }`, `edge.add`·`edge.remove { src, dst, kind }`, `category.create { name, slug?, color?, description? }`, `category.assign { target_id, base_version, category_id }`. 앞 변경이 만든 것은 `@번호`로 가리킨다 (토큰 하나에 제출 한 번이라 만들고 잇는 일을 한 묶음에 넣는다). 작업은 이벤트가 아니라 러너의 `submit_result`로 끝난다. 끝내는 길이 하나라 둘이 겹치지 않고, 러너가 도중에 죽어도 `change_sets.job_id`가 유일해서 같은 묶음은 한 번만 적용된다.
- `ai_login`은 콘솔에 넣은 AI 토큰을 러너에게 건넨다. 러너는 메모리에만 두고 AI CLI를 띄울 때 환경 변수로만 넘긴다. `POST /api/ai/claude/test`는 `ai_test` 작업을 만들어 러너가 실행한다 (서버 본체에는 AI가 없다). 이 일은 에이전트가 없어 `next_jobs`의 `agent`와 `run_token`이 null이고, 러너 `.env`에 토큰이 있어도 콘솔의 토큰으로 시험한다. 도는 사이 토큰을 바꾸면 옛 토큰의 결과는 버린다. `ai_login`은 기기만 부를 수 있고 만료된 토큰은 주지 않는다. 러너가 일을 빌리기 전에 토큰을 묻지 않는다: 쓸 로그인이 있는지는 서버가 `next_jobs`에서 본다. `ai_login`의 `version`은 실행하는 동안 CLI가 갱신한 자격을 `ai_login_refresh`로 되돌려 쓸 때 보낸다. 되돌려 쓰기는 갱신 토큰이 바뀌는 도구(Codex)만, 그 일을 쥔 러너만, 그 일이 쓴 도구만, 받은 판일 때만이다(다르면 `conflict`: 다른 실행이 먼저 바꿨다). 만료와 연결 확인 결과는 그대로 둔다.
- 웹 로그인: `POST /api/ai/:tool/signin`이 `ai_signin` 작업을 만들고(에이전트·작업 토큰 없음, 도구마다 하나), 러너가 로그인 명령(`claude setup-token` · `codex login --device-auth`)을 PTY에서 대신 돌린다. 러너는 화면에서 찾은 주소(Codex는 코드도)를 `ai_signin { task_id, url, user_code? }`로 알리고, Claude면 주인이 붙여 넣은 코드를 `ai_signin { task_id }`로 2초마다 묻는다(`code`는 로그인이 끝날 때까지 물을 때마다 같은 값이 와서 응답을 잃어도 다시 받는다. 러너는 한 번만 쳐 넣는다. 10분이 지나면 null). 받은 자격은 `ai_signin { task_id, credential }`(Claude는 `sk-ant-oat01-` 토큰, Codex는 `auth.json` 원문 64KB까지)로 넘기면 서버가 같은 트랜잭션에서 잠가 저장하고 작업을 `done`으로 끝낸다. 주소는 정해진 출처·경로만(`AiSigninPolicy`), 그 작업의 임대를 쥔 러너만 부를 수 있다. 주인이 취소하면 `cancelled: true`가 오고 러너는 명령을 끈다. 실패는 `submit_result { status: failed }`이고, `done`은 자격으로만 끝나서 `submit_result`로는 거절한다(`rule_violation`). 끝나거나 러너가 돌려준 로그인 작업에는 주소도 코드도 남기지 않는다(`payload`는 `{ tool }`만). 작업 상세(`GET /api/tasks/:id`)에는 코드의 암호문도 내보내지 않는다. 자격을 넘긴 응답을 잃고 다시 보내면 같은 답(`status: done`)을 준다. 동시에 두 번 시작해도 작업은 하나다(공간·도구마다 advisory 잠금). 주소·코드·자격은 실행 기록에 남기지 않는다. 웹 터미널은 아니다: 오가는 것은 주소, 사람이 붙여 넣은 코드 하나, 받은 자격뿐이다.
- `GET /api/notifications`는 `{ unread, notifications: [{ id, kind, severity, title, body, link, createdAt, read }] }`(최근 30개), `POST /api/notifications/read { ids? }`는 `{ read }`(ids가 없으면 모두). 주인만. 무엇을 알리는지는 알리는 모듈이 정하고(종류는 `GET /api/notice-settings`의 `kinds`), 콘솔은 변경 신호 `platform.notification`으로 바로 다시 읽는다. 푸시로 가는 내용은 `{ title, body, link, tag }`이고 서비스 워커(`/sw.js`)가 알림으로 띄운다. 누르면 같은 출처의 `link`만 연다.
- `GET /api/wiki-scores`는 `{ halfLifeDays, cited, groups: [{ categoryId, name, wikis: [점수] }], history: [점수] }`, `GET /api/wiki-scores/:id`는 `{ wiki: 점수, bases: [{ wikiId, title, ratio, amount }] }`다. 점수는 `{ id, title, categoryId, visibility, score(0~100), total, accumulated, inherited, uses, lastUsedAt, replacedBy }`. 읽을 때 계산하고 주인만 본다 (비공개 쓰임이 섞인 값, [wiki 점수](wiki점수.md)).
- `GET /api/graph`와 `GET /api/graph/public`은 `{ nodes: [{ id, kind, label, parent, visibility?, slug? }], edges: [{ src, dst, kind }] }`를 돌려준다. 공개 글이 가리키는 비공개 wiki는 이름 없는 자리(`private-<해시>`)로만 나오고, 진짜 id는 UUIDv7이라 날짜가 드러나서 내보내지 않는다. `neighbors { node_id }`는 `{ node, neighbors: [{ id, kind, label, relation }] }`.
- 결재한 공개의 결과는 `blog.post.published`와 `blog.post.publish_failed`에 `approvalId`, `outcome`을 실어 알린다. 없는 글이나 이미 공개한 글도 실패로 끝난다. `sns.post.send`는 아직 실행하는 곳이 없어 화면에서 고를 수 없다.
- 결재에서 고쳐 달라고 하면 작업이 대기로 돌아가고, 다음 `next_jobs`의 `target`은 결재의 대상이다.
- 만들기 작업의 재료: 러너는 AI를 띄우기 전에 `payload.make.outputs`의 결과물을 하나씩 `begin_download`로 표를 받아 `GET {download_path}`(머리글 `{header}: {token}`)로 받고, 크기 · sha256을 맞춰 작업 자리의 `inputs/`에 둔다. 표는 그 실행 · 결과물에 묶여 10분이다. 재료 위키는 받지 않는다: 작업 토큰에 그 위키의 읽기 허락이 봉인되어 AI가 `get_wiki`로 읽는다 (읽기 권한이 없어도 `get_wiki`가 열리고, 고른 위키만 읽힌다. `search_wikis` · `neighbors`에는 허락이 없다)
- 결과물: 러너는 AI가 일을 잘 끝냈을 때(제출 전) outputs 폴더의 파일을 하나씩 `begin_upload`로 표를 받아 `PUT {upload_path}`(머리글 `{header}: {token}`)로 보낸다. 표는 임대를 쥔 이번 실행에만 주고(진행 중 · 그 러너 · 임대가 살아 있음), 그 실행 · 이름 · 크기 · sha256에 묶여 10분이다. 파일 본문은 MCP로 보내지 않는다: AI 토큰은 `/mcp`에서만 요청자가 되고 JSON은 512KB까지라서다. 한도는 파일 하나 100MB, 실행 한 번 200개 · 합쳐 1GB, 공간 전체(`MOIDA_OUTPUTS_MAX_GB`, 기본 80), 디스크 여유(`MOIDA_DISK_RESERVE_GB`, 기본 20)이고 넘으면 `rule_violation`. 표를 줄 때 미리 보고, 받을 때 공간을 잠그고 다시 센다
- 도구 입력 모양을 바꾸면 `skills/`를 함께 고친다.

## 5. 작업 토큰

러너가 작업을 받으면 서버가 그 에이전트의 권한만 담은 토큰을 함께 준다. `SecretBox.pack`으로 만들어 저장하지 않고, 임대가 끝나면 함께 끝난다. AI CLI는 이 토큰만 받는다. 토큰은 `/mcp`에서만 Actor가 된다. REST에서 쓰면 호출마다 하는 작업 확인을 건너뛰기 때문이다. `ActorGuard`가 토큰을 읽어 Actor를 만들고, 호출마다 작업이 살아 있는지는 `mcp` 모듈이 `task`에 묻는다 (`account`는 `task`를 모른다).

| 값 | 내용 |
|---|---|
| Actor | `AgentActor(spaceId, agentId, taskId, scopes)` |
| 권한 | 에이전트에 정해 둔 권한만 |
| 만료 | 호출마다 임대가 살아 있는지 확인한다. 토큰 자체의 상한은 24시간이다. AI CLI는 받은 토큰을 바꿔 끼울 수 없어서, 임대가 늘어도 끊기지 않게 넉넉히 둔다 |

AI가 세션이나 메일 속 지시문에 속아도 이 권한을 넘을 수 없다.

## 6. 실시간 (SSE)

| 항목 | 규칙 |
|---|---|
| 내용 | 변경 신호만 보낸다 (`{ topic, id }`). 화면은 REST로 다시 읽는다 |
| 머리글 | `Content-Type: text/event-stream`, `Cache-Control: no-store, no-transform` |
| 유지 | 25초마다 빈 주석을 보낸다 |
| 재연결 | 브라우저 기본 재연결 후 화면이 다시 읽는다. 놓친 신호는 되돌리지 않는다. 서버가 오류로 답해 브라우저가 포기하면 `use-live`가 3초 뒤 다시 연다 |
| 서버 | Postgres `LISTEN/NOTIFY`를 `platform/stream`이 받아 전달. 내용은 항상 테이블에 있다 |

`no-transform`이 없으면 Next의 압축 때문에 스트림이 끝날 때 한꺼번에 도착한다 (Next 16.4.2의 `next start`, `next dev` rewrite에서 시험, 2026-10-31).

**WebSocket을 쓰지 않는 이유**: 콘솔은 받기만 하고 보내는 일은 REST로 충분하다. 웹 터미널과 공동 편집을 두지 않는다. WebSocket이 필요해지면 고칠 곳은 `platform/stream`과 웹의 `useLive` 훅 두 곳이다.

## 7. 큐

Redis 없이 Postgres로 한다. 큐와 DB가 나뉘면 원본이 둘이 되고 설치할 서비스가 하나 늘어난다. MCP 요청은 큐에 넣지 않고 바로 처리해 결과를 돌려준다. 큐는 요청 뒤의 일에만 쓴다.

| 일 | 저장 위치 | 처리 | 실패 처리 |
|---|---|---|---|
| 모듈 이벤트 | `platform.outbox` | 일꾼 | 지수 백오프. 8번 실패하면 멈추고 관리자에게 알림(`platform.event.failed`, 즉시), 다시 시도는 관리자가 (`api/events`) |
| AI 작업 | `task.tasks` | 러너 (`FOR UPDATE SKIP LOCKED`) | 임대 만료 후 재시도, 3회 실패 시 실패 표시 |
| 스케줄 (7단계) | `task.schedules` | 일꾼이 켜진 스케줄의 가장 이른 다음 시각에 깨어 작업 생성 (스케줄을 저장하면 깨운다) | `requestId`로 중복 방지, 하루 한도 |
| 브라우저 푸시 (7단계) | `platform.notifications` (`push_sent_at`이 빈 것) | 일꾼이 알림이 남으면 깨어(남은 것은 조용한 시간이 끝날 때 · 묶음 시각에), 짧은 트랜잭션에서 다룬 것으로 적고 밖에서 보낸다 | 많아야 한 번 (실패해도 다시 보내지 않고 알림 센터에 남음). 404 · 410이나 다섯 번 실패한 구독은 지운다 |

`NOTIFY`는 깨우기 신호로만 쓴다. 신호를 놓쳐도 다음 조회에서 찾는다. 일꾼은 `moida_outbox`를 듣고(끊기면 다시 듣는다) 마감 타이머로만 깬다: 쉬는 동안 조회하지 않는다 (리팩토링 2단계). 콘솔과 러너의 긴 폴링은 `moida_changes`를 쓴다. 실행 기록 신호에 일꾼이 깨지 않게 채널을 나눴다.

**Redis를 다시 볼 조건**: API 서버 여러 대, 실시간 메시지 초당 수천 건, 러너 수십 대 동시 실행. 그때도 `platform/base`의 클래스만 바꾼다.
